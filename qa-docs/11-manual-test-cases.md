## Полные сценарии

## 01 Авторизация

### TC-013 — Деактивация обрывает уже открытую сессию

**Приоритет:** Высокий  
**Режим:** Ручной

**Предусловия**

Два браузера (или обычное + приватное окно): в одном залогинен тестовый оператор, в другом — его РОП.

**Шаги**

1. В браузере №1 оператор работает (открыт раздел «Звонки»).
2. В браузере №2 РОП деактивирует этого оператора («Операторы» → меню действий → «Деактивировать»).
3. В браузере №1 продолжай пользоваться разделами и наблюдай до 20 минут.

**Ожидаемый результат**

Не позже чем через ~15–20 минут оператора выбрасывает на страницу входа (продление сессии отклонено). Если сессия живёт дольше и работает как ни в чём не бывало — это воспроизведение BUG-006, отметь в фактическом результате.

### TC-019 — Долгая работа без выхода: сессия продлевается незаметно

**Приоритет:** Средний  
**Режим:** Ручной

**Предусловия**

Вход под любой ролью.

**Шаги**

1. Открой любой раздел с данными (например, «Операторы»).
2. Оставь вкладку открытой на 20 минут, ничего не нажимая.
3. Вернись и перейди в другой раздел меню.

**Ожидаемый результат**

Раздел открывается, данные загружаются. Повторный ввод логина и пароля НЕ требуется — продление произошло незаметно.

## 02 Права и изоляция

### TC-042 — API: РОП-А не читает данные оператора РОП-Б

**Приоритет:** Критический  
**Режим:** Ручной

**Предусловия**

Известны {STAGE_API_URL}, логин/пароль РОП-А и ID любого оператора РОП-Б (ID виден в адресной строке карточки оператора при входе под РОП-Б: /dashboard/operators/ЭТОТ-ДЛИННЫЙ-НОМЕР).

**Шаги**

1. Открой терминал.
2. Получи токен РОП-А (как в TC-041, шаг 2, только с логином и паролем РОП-А).
3. Запроси карточку чужого оператора (подставь токен РОП-А и ID оператора РОП-Б):
      curl -i {STAGE_API_URL}/v1/users/ID_ОПЕРАТОРА_РОП_Б -H "Authorization: Bearer ТОКЕН"
4. Посмотри код ответа и тело.

**Ожидаемый результат**

Код ответа 403 или 404 — оба допустимы. В теле НЕТ данных оператора: ни имени, ни телефона, ни зарплаты, ни внутреннего номера. Если данные вернулись — критический дефект изоляции (R-1), баг немедленно.

## 03 Пользователи

### TC-045 — Создание РОП с пустыми обязательными полями запрещено

**Приоритет:** Высокий  
**Режим:** Ручной

**Предусловия**

Выполнен вход под супер-админом, открыт раздел «РОПы».

**Шаги**

1. Нажми «Новый РОП».
2. Ничего не вводи и по очереди нажми в каждое поле, затем щёлкни вне поля.
3. Посмотри на подсказки под полями.
4. Проверь состояние кнопки «Создать».

**Ожидаемый результат**

Под пустыми полями показаны понятные сообщения: «Имя обязательно», «Фамилия обязательна», «Телефон обязателен», «Имя пользователя обязательно», «Название компании обязательно» и требование к паролю. Кнопка «Создать» неактивна, пользователь не появляется.

### TC-046 — Телефон РОП принимает только номер Узбекистана

**Приоритет:** Высокий  
**Режим:** Ручной

**Предусловия**

Выполнен вход под супер-админом, открыта форма «Создать РОП». Остальные поля заполнены корректными уникальными значениями.

**Шаги**

1. В поле «Телефон» введи буквы, например «абвгд».
2. Щёлкни вне поля и прочитай сообщение.
3. Замени значение на слишком короткий номер «+998 90 123».
4. Щёлкни вне поля и снова проверь сообщение.
5. Введи корректный тестовый номер в формате «+998 90 123 45 67».

**Ожидаемый результат**

Для букв и короткого номера показано «Неверный номер телефона (+998 XX XXX XX XX)», создание недоступно. После корректного номера ошибка исчезает.

### TC-061 — Деактивация оператора действует сразу и не удаляет историю

**Приоритет:** Критический  
**Режим:** Ручной

**Предусловия**

В одном браузере выполнен вход под РОП, в другом — под отдельным тестовым оператором. У оператора есть история звонков.

**Шаги**

1. Под РОП нажми «Деактивировать» у оператора.
2. Под оператором обнови страницу или открой другой раздел.
3. Проверь, что оператор сразу возвращён на вход или получил отказ.
4. Под РОП открой карточку оператора и проверь историю.
5. Нажми «Активировать», затем снова войди под оператором.

**Ожидаемый результат**

Доступ прекращается на следующем запросе. История звонков, рабочие часы, внутренний номер и воронки остаются. После активации оператор снова входит.

**Приоритет:** Высокий  
**Режим:** Ручной

**Предусловия**

**Шаги**

1. Войди под оператором после начала рабочего дня.
2. Открой «Обзвон» и нажми «Начать обзвон».
3. Для каждого выданного лида сразу нажимай «Пауза», затем «Пропустить», чтобы не звонить.
4. Повторяй, пока проверишь все пять лидов.

**Ожидаемый результат**

Все пять лидов попадают в очередь как один класс «Не поднял трубку». Ни один вариант апострофа не пропадает.

### TC-080 — Только точное имя поля call vaqti задаёт время прихода

**Режим:** Ручной

**Предусловия**

**Шаги**

2. Открой «Обзвон» при параметре «Время звонка перед приходом» = 60 минут.

## 05 Очередь обзвона

### TC-092 — Счётчик показывает только доступные лиды оператора

**Приоритет:** Высокий  
**Режим:** Ручной

**Предусловия**

Для оператора подготовлена отдельная тестовая воронка. В ней ровно 3 доступных лида и по одному закрытому, удалённому и отложенному лиду. Другие операторы тестовую воронку сейчас не обзванивают.

**Шаги**

1. Войди под тестовым оператором.
2. В левом меню открой «Режим звонков» — экран с заголовком «Обзвон».
3. Посмотри число над подписью «лидов в очереди».
4. Сверь имена трёх доступных лидов с подготовленным списком.

**Ожидаемый результат**

Счётчик равен 3. Закрытый, удалённый, отложенный и недоступный оператору лиды в это число не входят.

### TC-093 — Счётчик очереди обновляется каждые 30 секунд

**Приоритет:** Средний  
**Режим:** Ручной

**Предусловия**

Под оператором открыт экран «Обзвон». РОП может добавить тестовый лид в назначенную этому оператору воронку. Окно с инструкцией перед звонком закрыто.

**Шаги**

1. Запиши текущее число «лидов в очереди».
2. В AmoCRM создай доступный сейчас тестовый лид со статусом «Yangi lid».
3. Не обновляй страницу Operator AI.
4. Подожди 35 секунд и снова посмотри на число.

**Ожидаемый результат**

Не позднее чем через 30–35 секунд счётчик увеличивается на 1. Страница не мигает и не создаёт дубликат лида.

### TC-094 — Очередь соблюдает порядок пяти классов

**Приоритет:** Критический  
**Режим:** Ручной

**Предусловия**

В одной назначенной оператору воронке подготовлено по одному доступному сейчас лиду каждого из пяти классов. Имена лидов начинаются с номера ожидаемого порядка: 1-Bugun, 2-Keyingi, 3-Chala, 4-Kotarmadi, 5-Yangi.

**Шаги**

1. Войди под оператором и открой «Обзвон».
2. Нажми «Начать обзвон».
3. Запиши имя выданного лида и нажми «Пропустить».
4. Повтори предыдущий шаг, пока не увидишь все пять тестовых лидов.
5. Сравни записанный порядок с номерами в именах.

**Ожидаемый результат**

Лиды выдаются строго так: 1-Bugun, 2-Keyingi, 3-Chala, 4-Kotarmadi, 5-Yangi. Пропущенный лид не появляется снова в этом же проходе.

Первым выдан «QA-старый». Порядок не меняется после обновления страницы.

### TC-096 — Будущее время звонка откладывает даже приоритетный лид

### TC-097 — Оператор получает лиды только назначенной воронки

**Приоритет:** Критический  
**Режим:** Ручной

**Предусловия**

У РОП есть две тестовые воронки A и B, в каждой по одному доступному лиду. Оператору назначена только воронка A.

4. Открой «Обзвон», нажми «Начать обзвон» и поставь таймер на паузу.
5. Проверь имя и воронку выданного лида.

**Ожидаемый результат**

Оператор получает только лида из воронки A. Лид из B не входит в его счётчик и не выдаётся.

### TC-098 — Оператор работает с несколькими назначенными воронками

**Приоритет:** Высокий  
**Режим:** Ручной

4. Нажми «Начать обзвон» и сразу «Пауза».
5. Посмотри, из какой воронки пришёл первый лид.

**Ожидаемый результат**

В счётчике 2 лида. Первым выдан «Bugun keladi» из воронки B, потому что приоритет класса важнее принадлежности к воронке.

### TC-100 — Два оператора одновременно получают разных лидов

Операторы получают двух разных лидов. Один и тот же телефон не показан одновременно в обоих окнах.

### TC-101 — Захваченный лид недоступен другому оператору пять минут

У оператора B счётчик не включает захваченный лид, и этот лид ему не выдаётся.

### TC-102 — Долгий звонок не допускает двойного обзвона после пяти минут

**Приоритет:** Критический  
**Режим:** Ручной

**Предусловия**

**Ожидаемый результат**

Без возврата на главный экран открывается другой, второй лид. Остаток очереди уменьшается; уже обработанный лид повторно не выдаётся немедленно.

### TC-106 — «Пропустить» откладывает лид на 30 минут без попытки

**Режим:** Ручной

5. Через карточку лида или тестовый API проверь время следующего звонка и число попыток.

**Ожидаемый результат**

Лид исчезает из текущей очереди, следующее время — примерно через 30 минут (допуск 1 минута). Число попыток не изменилось.

До назначенного времени счётчик равен 0. После наступления времени лид возвращается в счётчик и снова выдаётся.

### TC-108 — Очередь восстанавливается после временной потери сети

**Ожидаемый результат**

Каждый неверный вариант отклонён с понятной красной подсказкой. Исходные настройки на сервере не изменились.

### TC-112 — Новый критерий действует со следующего расчёта

**Режим:** Ручной

3. Под оператором выполни недозвон по лиду B и подтверди итог «Ko'tarmadi».
4. Проверь время следующего звонка обоих лидов.
5. Верни исходную настройку.

**Ожидаемый результат**

У лида A остаётся старое сохранённое время. Для нового расчёта лида B используется интервал 15 минут.

### TC-113 — После конца рабочего дня повтор переносится на завтра

**Приоритет:** Высокий  
**Режим:** Ручной

**Предусловия**

На тестовом РОП начало дня 08:00, конец установлен на 5 минут позже текущего времени, интервал повтора — 15 минут. Есть тестовый лид «Ko'tarmadi».

4. После конца рабочего дня обнови «Обзвон».
5. Верни исходные критерии.

**Ожидаемый результат**

Повтор назначен на начало следующего рабочего дня, а не через 15 минут ночью. После конца дня лид не выдаётся. Если выдаётся, поле «Окончание рабочего дня» не подключено к очереди.

### TC-114 — Договорённость без часа использует заданное время

**Режим:** Ручной

**Предусловия**

У РОП значение поля равно 10:15. Есть тестовая запись разговора, где клиент называет будущий день, но не называет час. Gemini на стенде доступен.

## 06 Звонок (цикл)

### TC-115 — Перед звонком показана понятная инструкция по лиду

**Приоритет:** Высокий  
**Режим:** Ручной

**Предусловия**

У РОП настроены текст совета, форма с обязательным и необязательным полями и статусы. В очереди оператора есть тестовый лид с именем, телефоном, суммой и статусом.

**Шаги**

1. Войди под оператором, открой «Обзвон» и нажми «Начать обзвон».
2. Сразу нажми «Пауза».
3. Сверь имя, телефон, текущий статус и сумму с тестовым лидом.
4. Прочитай блоки «Причина звонка», «Совет ИИ», «Целевые статусы» и «Поля, заполняемые ИИ».
5. Проверь, что обязательные поля отмечены маленькой цветной точкой.

**Ожидаемый результат**

Данные относятся к выданному лиду. Совет совпадает с настройкой РОП. Показаны реальные статусы воронки и реальные поля формы; обязательные поля отмечены.

### TC-116 — Первый контакт не показывает попытку 0/4

**Приоритет:** Средний  
**Режим:** Ручной

**Предусловия**

В очереди есть новый лид без прошлых звонков, времени последней попытки и предыдущего статуса.

**Шаги**

1. Открой инструкцию этого лида и нажми «Пауза».
2. Найди блок «Причина звонка».
3. Прочитай главный текст и строки под ним.

**Ожидаемый результат**

Показан текст «Новый лид — вы связываетесь впервые…». Нет строк «Попытка 0/4», «Прошлый этап» с пустым значением или неверного времени.

### TC-117 — Повторный звонок показывает номер попытки и прошлый этап

**Приоритет:** Высокий  
**Режим:** Ручной

**Предусловия**

Есть лид «Ko'tarmadi» с двумя завершёнными попытками из четырёх, известным предыдущим статусом и заполненным временем встречи либо прихода.

**Шаги**

1. Открой инструкцию этого лида и нажми «Пауза».
2. В блоке «Причина звонка» найди строки «Попытка», «Прошлый этап» и «Последняя попытка».
3. Если подготовлено время встречи/прихода, найди соответствующую строку.
4. Сверь каждое значение с карточкой и историей тестового лида.

**Ожидаемый результат**

Показано «Попытка 2/4», правильный прошлый этап и правильные дата/время. Значения не перепутаны между лидами.

### TC-118 — Последняя попытка выделена как важная

**Приоритет:** Средний  
**Режим:** Ручной

**Предусловия**

Максимум попыток равен 4. Есть лид «Ko'tarmadi» с тремя уже записанными попытками.

**Шаги**

2. Проверь строку «Попытка».
3. Сравни цвет левой полосы и заголовка блока «Причина звонка» с обычным повторным лидом.

**Ожидаемый результат**

Показано «Попытка 3/4», а блок выделен янтарным цветом. Инструкция и кнопки остаются читаемыми.

### TC-119 — Неполные данные причины не ломают инструкцию

**Приоритет:** Высокий  
**Режим:** Ручной

**Предусловия**

Есть доступный лид без предыдущего статуса, времени встречи, времени прихода и истории попыток. Имя или сумма также могут быть пустыми.

**Шаги**

1. Открой инструкцию этого лида и нажми «Пауза».
2. Просмотри блок «Причина звонка» и верхнюю строку окна.
3. Нажми «Продолжить», затем снова «Пауза».

**Ожидаемый результат**

Окно открывается без белого экрана и технической ошибки. Пустые строки не показываются; для пустого имени используется «Лид без имени». Таймер и кнопки работают.

### TC-120 — В итогах доступны только статусы воронки лида

**Приоритет:** Критический  
**Режим:** Ручной

**Предусловия**

У РОП две воронки с разными статусами. Для теста поочерёдно подготовлены два состояния: форма со статусами и форма без них. Есть лид в воронке A.

**Шаги**

1. Проведи тестовый звонок до экрана «Итог разговора — подтвердите».
2. Раскрой поле «Статус» и запиши варианты.
3. Проверь, что нет статусов воронки B, «Неразобранное», системных 142/143, «Yangi» и «Sifatsiz».
4. Повтори проверку после удаления настроенных статусов формы у РОП.

**Ожидаемый результат**

В обоих состояниях список не пуст и содержит только допустимые живые статусы воронки A. Чужие и системные этапы выбрать нельзя.

### TC-121 — Через 10 секунд номер набирается автоматически

**Приоритет:** Высокий  
**Режим:** Ручной

**Предусловия**

**Шаги**

1. Нажми «Начать обзвон».

3. Засеки время от появления 10 до начала набора.
4. Проверь состояние в верхней строке окна.

**Ожидаемый результат**

Число уменьшается раз в секунду. Примерно через 10 секунд начинается один звонок, верхняя строка меняется на «В ЭФИРЕ».

### TC-122 — «Пауза» останавливает таймер, «Продолжить» возобновляет

**Приоритет:** Высокий

### TC-123 — «Позвонить сейчас» начинает только один звонок

**Режим:** Ручной

Открыта инструкция, телефония готова, тестовый телефон находится у тестировщика.

**Шаги**

Начинается ровно один вызов. Открыт один экран разговора; на телефоне нет двух параллельных или последовательных дублей от двойного клика.

### TC-124 — Звонок из браузера проходит полный путь

**Приоритет:** Критический  
**Режим:** Ручной

**Предусловия**

Для оператора настроен и зарегистрирован браузерный телефон WebRTC/Verto. Разрешён доступ браузера к микрофону. Тестовый телефон может принять вызов.

3. Убедись, что появилась подпись «Идёт разговор» и таймер 0:01, 0:02…
4. Скажи короткую тестовую фразу в микрофон.
5. Нажми «Завершить звонок».

**Ожидаемый результат**

Клиент и оператор слышат друг друга. Таймер начинается только после ответа. После завершения открывается экран итога, окно не зависает в состоянии вызова.

### TC-125 — При недоступном WebRTC используется звонок через сервер

**Приоритет:** Высокий  
**Режим:** Ручной

**Предусловия**

На тестовом РОП WebRTC недоступен (запрос учётных данных возвращает 404/409), но click-to-call OnlinePBX настроен и внутренний номер оператора активен.

**Шаги**

1. Открой инструкцию и дождись, пока исчезнет текст «Браузерный телефон подключается…».
2. Нажми «Позвонить сейчас».
3. Прими сначала вызов на телефоне/софтфоне оператора, затем дождись соединения с тестовым лидом.
4. Заверши разговор и дождись экрана итога.

**Ожидаемый результат**

Вызов проходит через OnlinePBX и относится к правильному лиду. Система не остаётся бесконечно на подготовке WebRTC и после звонка показывает итог.

### TC-126 — Ошибка телефонии не считается состоявшимся звонком

**Режим:** Ручной

2. Нажми «Позвонить сейчас».
3. Прочитай сообщение об ошибке.
4. Верни телефонию в рабочее состояние.
5. Повтори звонок этому же лиду.

**Ожидаемый результат**

Показана понятная ошибка начала звонка, а не белый экран. Лид остаётся доступен этому оператору, попытка не увеличилась. После восстановления звонок можно повторить.

### TC-127 — Недозвон открывает ручной итог без автоматического статуса

**Режим:** Ручной

2. Дождись окончания вызова.
3. Проверь заголовок экрана итога и выбранное значение поля «Статус».
4. Не нажимай «Подтвердить», пока не проверишь остальные поля.

**Ожидаемый результат**

Открывается «Итог разговора — подтвердите», а не рекомендация ИИ. Поле «Статус» пустое до решения человека; нет выдуманной расшифровки или итогового текста.

### TC-128 — Введённое во время разговора переносится в итог

**Приоритет:** Высокий  
**Режим:** Ручной

**Предусловия**

В форме РОП есть текстовое поле и поле даты. Браузерный звонок доступен.

**Шаги**

1. Начни звонок и ответь на тестовом телефоне.
2. В блоке «Заполнение во время разговора (необязательно)» введи заметный тестовый текст и дату.
3. Нажми «Завершить звонок».

**Ожидаемый результат**

Ошибка объяснима и не маскируется ложным успехом. После возврата API кабинет снова работает без нового запуска; неподтверждённые данные не отправлены и не подменены.

### TC-381 — Перезапуск бэкенда не создаёт второго захвата активного лида

**Приоритет:** Критический  
**Режим:** Ручной

**Предусловия**

Только staging. Оператор захватил тестового лида, но звонок ещё не начат. Согласован перезапуск одного экземпляра бэкенда.

**Шаги**

1. Запиши session ID, lead ID и число попыток.
2. Перезапусти бэкенд согласованным способом.
3. После готовности обнови режим обзвона того же оператора.
4. Одновременно запроси следующего лида вторым оператором.
5. Проверь сессии, блокировки и попытки через API.

**Ожидаемый результат**

Первый оператор получает ту же активную сессию либо понятный безопасный возврат. Второй не получает этого лида, новой попытки и второй активной сессии не создаётся.

### TC-383 — Обновление токена во время заполнения не стирает форму

**Приоритет:** Критический  
**Режим:** Ручной

**Предусловия**

Access token тестового оператора близок к истечению. Открыт итог звонка с несколькими незаполненными полями; автотаймер поставлен на паузу.

**Шаги**

1. Заполни несколько полей заметными значениями.
2. Дождись истечения access token.
3. Выполни безопасный запрос, вызывающий refresh.
4. Проверь Network и все введённые значения.
5. Сними паузу и подтверди результат один раз.

**Ожидаемый результат**

Refresh проходит один раз, исходный запрос повторяется после него. Форма и таймер сохраняются; в AmoCRM уходит один подтверждённый результат.

### TC-384 — Десять операторов одновременно получают разные лиды

**Приоритет:** Критический  
**Режим:** Ручной

**Предусловия**

Есть 10 тестовых операторов одного РОП, назначенная воронка и минимум 15 доступных лидов. До запуска согласован допустимый порог времени ответа.

**Шаги**

1. Подготовь 10 независимых сессий операторов.
2. Одновременно нажми Начать обзвон во всех сессиях.
3. Запиши время ответа, lead ID и session ID каждого.
4. Сравни уникальность ID и состояние оставшейся очереди.
5. Заверши или безопасно пропусти тестовые сессии.

**Ожидаемый результат**

Все ответы укладываются в согласованный порог, 500/502 нет. Выдано 10 разных лидов и 10 сессий; остаток очереди уменьшился ровно на 10.

### TC-385 — Последовательные правки AmoCRM и оператора не теряются молча

**Приоритет:** Критический  
**Режим:** Ручной

**Предусловия**

У тестового лида есть безопасное текстовое поле. Зафиксировано точное время каждого изменения и доступна история AmoCRM.

**Шаги**

1. Сначала измени поле в AmoCRM, дождись синхронизации, затем задай другое значение в Operator AI.
2. Сверь обе системы и историю.
3. Повтори на другом поле в обратном порядке: Operator AI, затем AmoCRM.
4. Дождись фоновой и webhook-синхронизации.
5. Сравни финальные значения и журналы.

**Ожидаемый результат**

После каждого порядка обе системы сходятся на последнем подтверждённом значении. Предыдущее изменение видно в истории/журнале; нет третьего старого значения или дубля сделки.

### TC-386 — Запоздавший старый вебхук не откатывает свежие данные

**Приоритет:** Критический  
**Режим:** Ручной

**Предусловия**

Можно безопасно повторить сохранённый старый webhook тестового лида после нового изменения.

**Шаги**

1. Сохрани payload события со значением A.
2. В AmoCRM измени то же поле на B и дождись синхронизации.
3. Отправь старый payload A повторно.
4. Обнови карточку Operator AI и AmoCRM.
5. Проверь локальное зеркало и журнал обработки.

**Ожидаемый результат**

Финальное значение остаётся B в обеих системах. Старое событие не откатывает данные, не создаёт новую сделку и не ломает последующие вебхуки.

### TC-387 — Поздний результат AI не перезаписывает ручное подтверждение

**Приоритет:** Критический  
**Режим:** Ручной

**Предусловия**

На staging согласован контролируемо медленный AI-анализ; оператор может выполнить ручное подтверждение с отличимыми значениями.

**Шаги**

1. Запусти звонок и дождись начала медленного анализа.
2. Введи ручной статус и поля, затем подтверди один раз.
3. Запиши значения в AmoCRM.
4. Дождись позднего результата AI.
5. Снова проверь сессию, форму и AmoCRM.

**Ожидаемый результат**

Ручное подтверждение остаётся финальным. Поздний AI не создаёт вторую отправку, не меняет статус/поля и не возвращает закрытую сессию в работу.

### TC-388 — Некорректный ответ AI не ломает звонок и форму

**Приоритет:** Критический  
**Режим:** Ручной

**Предусловия**

На staging доступна заглушка или безопасный способ вернуть некорректный AI-ответ без обращения к production.

**Шаги**

1. По очереди верни невалидный JSON, неизвестный status ID и неверный enum.
2. Для каждого варианта дождись экрана результата.
3. Проверь сообщение, поля и выбранный статус.
4. Заполни корректный ручной результат.
5. Подтверди и проверь AmoCRM.

**Ожидаемый результат**

Нет белого экрана и автоматической отправки мусора. Неизвестные статус/enum не принимаются; оператор видит понятное состояние и успешно сохраняет ручной результат.

### TC-389 — Повреждённое аудио не вызывает бесконечные повторы

**Приоритет:** Критический  
**Режим:** Ручной

**Предусловия**

Подготовлены три безопасных тестовых события: пустой файл, обрезанный файл и неподдерживаемый формат. Есть доступ к журналу staging.

**Шаги**

1. По очереди отправь три события на обработку.
2. Наблюдай статусы и число попыток в течение окна retry.
3. Параллельно обработай одну корректную короткую запись.
4. Проверь сообщения интерфейса и журнал.
5. Повтори открытие проблемных звонков.

**Ожидаемый результат**

Проблемные записи завершаются контролируемой ошибкой не более установленного лимита попыток. Корректная запись обрабатывается; память и очередь не растут бесконечно.

### TC-390 — Длинный разговор обрабатывается без молчаливого обрезания

**Приоритет:** Высокий  
**Режим:** Ручной

**Предусловия**

Есть согласованная длинная тестовая запись с контрольными фразами в начале, середине и конце; её обработка не нарушает лимит тестового AI.

**Шаги**

1. Загрузи или создай длинный тестовый звонок.
2. Дождись обработки в пределах согласованного максимального времени.
3. Найди все три контрольные фразы в транскрипции.
4. Сверь резюме и извлечённые поля.
5. Проверь журнал на таймауты и повторные анализы.

**Ожидаемый результат**

Все контрольные части учтены либо пользователь получает явное сообщение о лимите; молчаливого обрезания нет. Анализ создаётся один раз и не блокирует другие звонки.

### TC-391 — Отказ в доступе к микрофону даёт рабочий выход

**Приоритет:** Критический  
**Режим:** Ручной

**Предусловия**

В браузере для staging явно запрещён доступ к микрофону; серверный click-to-call либо инструкция по восстановлению доступны согласно конфигурации.

**Шаги**

1. Открой режим обзвона и захвати тестового лида.
2. Дождись окончания попытки подготовки WebRTC.
3. Прочитай сообщение и доступные действия.
4. Разреши микрофон либо выбери предусмотренный fallback.
5. Повтори безопасный звонок.

**Ожидаемый результат**

Нет бесконечной подготовки и немого автоматического вызова. Пользователь получает понятный способ разрешить микрофон или рабочий fallback; повтор проходит успешно.

### TC-392 — Закрытие вкладки во время сессии не создаёт новый звонок

**Приоритет:** Критический  
**Режим:** Ручной

**Предусловия**

Оператор захватил лида; звонок начат или открыт итог, session ID записан.

**Шаги**

1. Во время выбранной фазы закрой вкладку браузера.
2. Снова открой кабинет и режим обзвона под тем же оператором.
3. Сравни lead ID и session ID.
4. Проверь попытки, блокировку и историю PBX.
5. Безопасно заверши восстановленную сессию.

**Ожидаемый результат**

Восстановлена та же сессия или показано её однозначное завершённое состояние. Второй вызов, новая попытка и новый захват этого лида не создаются.

### TC-393 — Сигнал занято учитывается как одна неудачная попытка

**Приоритет:** Критический  
**Режим:** Ручной

**Предусловия**

Тестовый номер контролируемо отвечает сигналом занято. Известны исходный статус и счётчик.

**Шаги**

1. Запусти один звонок на занятый номер.
2. Дождись завершения вызова и экрана итога.
3. Не выбирай статус и дождись обработки согласно правилу недозвона.
4. Проверь вызовы PBX, попытки, AI и AmoCRM.
5. Проверь время следующей доступности лида.

**Ожидаемый результат**

Есть один вызов и одна новая попытка; второго номера и AI-анализа нет. Статус AmoCRM не меняется автоматически, повтор планируется по настройкам.

### TC-394 — Очень короткий ответ не получает системный плохой статус

**Приоритет:** Высокий  
**Режим:** Ручной

**Предусловия**

Есть две короткие записи: человек отвечает нейтральной фразой и автоответчик. Воронка содержит рабочий статус и системные плохие статусы.

**Шаги**

1. Обработай короткий человеческий ответ.
2. Проверь транскрипцию, статус и поля.
3. Обработай запись автоответчика.
4. Сравни результат и число попыток.
5. Проверь доступные оператору варианты ручной коррекции.

**Ожидаемый результат**

Система не предлагает `Sifatsiz`/`Yangi`; состоявшееся соединение не становится `Ko'tarmadi` только из-за длины. Неуверенный результат можно исправить вручную.

### TC-395 — Две вкладки одного оператора не запускают два параллельных звонка

**Приоритет:** Критический  
**Режим:** Ручной

**Предусловия**

Один оператор вошёл в двух вкладках, в очереди минимум два лида.

**Шаги**

1. Одновременно открой режим обзвона в обеих вкладках.
2. Одновременно нажми Начать обзвон.
3. Сравни lead ID и session ID в Network.
4. Попробуй запустить набор из обеих вкладок.
5. Проверь OnlinePBX и активные сессии.

**Ожидаемый результат**

Обе вкладки видят одну активную сессию либо одна получает понятный отказ. Создан один вызов одному лиду; второй лид остаётся в очереди.

### TC-396 — Две компании параллельно проходят критический путь без смешения

**Приоритет:** Критический  
**Режим:** Ручной

**Предусловия**

Есть РОП-А и РОП-Б с отдельными тестовыми AmoCRM/OnlinePBX, операторами, статусами и полями.

**Шаги**

1. Одновременно запусти по одному звонку в каждой компании.
2. Заверши разговоры с разными статусами и значениями.
3. Дождись AI и синхронизации.
4. Проверь обе AmoCRM, истории звонков, очереди и журналы.
5. Сравни config, rop, operator, deal и field ID.

**Ожидаемый результат**

Каждая компания получает только свой звонок, анализ, статус и поля. Нет перекрёстных ID, токенов, аудио или задержки одной компании из-за ошибки другой.

### TC-397 — Новый клиент проходит путь от создания РОП до первого звонка

**Приоритет:** Критический  
**Режим:** Ручной

**Предусловия**

Только staging. Есть отдельные чистые тестовые AmoCRM и OnlinePBX, секреты в `.env`, уникальные данные нового клиента и тестовый лид.

**Шаги**

1. Супер-админ создай РОП и подключи обе интеграции.
2. Под РОП синхронизируй воронки, проверь правила и создай оператора с extension.
3. Назначь оператору воронку и сохрани критерии.
4. Под оператором начни смену, получи лида и выполни отвеченный звонок.
5. Подтверди результат и проверь AmoCRM, историю звонков и смену.

**Ожидаемый результат**

Новый клиент без ручной правки базы проходит весь путь до первого успешного звонка. Результат один раз записан в его AmoCRM; аудио/AI/смена относятся к новому оператору.

### TC-398 — Один лид проходит полный поддерживаемый жизненный цикл

**Приоритет:** Критический  
**Режим:** Ручной

**Предусловия**

В тестовой воронке настроены все поддерживаемые статусы и поля времени. Для фиолетовых функций используется только уже выпущенная часть скоупа.

**Шаги**

1. Создай Yangi-лида в AmoCRM и дождись Operator AI.
2. Проведи недозвон и проверь попытку без автосмены статуса.
3. Следующим отвеченным звонком назначь перезвон и дождись его очереди.
4. Назначь встречу, проверь переход в день визита и звонок за час.
5. Заверши лид поддерживаемым финальным статусом и проверь историю.

**Ожидаемый результат**

На каждом этапе статус, время, очередь и попытки соответствуют правилам. История и AmoCRM синхронны, лид не дублируется и после финала больше не выдаётся.

### TC-399 — Все бизнес-методы API проверены матрицей ролей

**Приоритет:** Критический  
**Режим:** Ручной

**Предусловия**

Сохранён OpenAPI проверяемого релиза и согласована матрица `метод × гость/super_admin/ROP/operator` с ожидаемыми кодами. Используются только безопасные тестовые ID.

**Шаги**

1. Исключи только служебные методы, явно помеченные вне продукта.
2. Для каждого бизнес-метода выполни запрос без токена.
3. Повтори под super_admin, ROP и operator с безопасным payload.
4. Для ID-методов повтори запрос со своим и чужим tenant ID.
5. Запиши все отклонения ожидаемого кода и наличие данных в ответе.

**Ожидаемый результат**

Каждая комбинация совпадает с утверждённой матрицей. Запрещённые запросы дают 401/403/404 без данных и побочных изменений; разрешённые работают только в своём tenant.

## Как использовать список

1. Выберите кейсы по изменённым разделам и рискам из [Release Gate](08-release-readiness.md).
2. Выполняйте функциональные шаги только на staging/test. Production разрешён только для пассивного наблюдения.
3. Зафиксируйте результат в [основном каталоге](07-test-cases.xlsx).
4. После появления pytest-автотеста перенесите кейс в [реестр автоматизированных кейсов](10-automated-test-cases.md).
