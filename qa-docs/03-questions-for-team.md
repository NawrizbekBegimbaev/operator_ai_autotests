<a id="q-01"></a>
## Q-01. Должен ли ROP управлять подключением к AmoCRM самостоятельно?

**Кому:** продакт (вопрос про замысел) + разработчик бэкенда (вопрос про реализацию)
**Важность:** высокая — затрагивает безопасность и разграничение прав
**Статус:** 🟡 Задан, ждём ответа
**Дата обнаружения:** 21.07.2026

### Суть простыми словами

Подключение к AmoCRM — это набор ключей доступа к CRM клиента (домен, client_id, client_secret, токены доступа). По документации этим занимается Super-admin: он заводит клиента и настраивает ему интеграции.

В интерфейсе так и есть — кнопка настройки AmoCRM показывается **только** Super-админу.

Но интерфейс — это лишь «витрина». Под ней есть API, к которому можно обратиться напрямую, минуя кнопки. И вот там ROP может делать со своим подключением к AmoCRM **всё, что угодно**: создать, посмотреть (включая секретные ключи), изменить и удалить.

Аналогия: на двери кабинета нет ручки, но дверь не заперта — достаточно толкнуть.

### Что говорит документация

**ТЗ, раздел 3.5 «Permission Matrix»:**

| Функция | Super Admin | ROP | Operator |
| --- | --- | --- | --- |
| Configure Integrations | ✅ | ❌ | ❌ |

ТЗ (раздел 3.2) относит настройку интеграций AmoCRM и OnlinePBX к зоне ответственности Super-admin. В обязанностях ROP (раздел 3.3) настройки интеграций **нет вообще**.

**MVP-Scope, раздел 2 «Admin (Super-admin)»:** строка «AmoCRM connection per ROP (CRUD) — In MVP — Done/Done» — то есть фича числится за админской частью.

### Что говорит код

**Бэкенд — доступ ROP открыт полностью.**

Проверка доступа к конфигу AmoCRM (`project/back/internal/usecase/amocrm/service.go:3153`):

```go
func canAccessConfig(principal entity.Principal, config entity.AmoCRMConfig) bool {
	switch principal.Role {
	case entity.RoleSuperAdmin:
		return true
	case entity.RoleROP:
		return config.ROPID == principal.UserID   // ← ROP допускается к своему конфигу
	default:
		return false
	}
}
```

При создании конфига (`service.go:1573`, функция `resolveConfigROPID`) для роли ROP код **молча подставляет его собственный id** — то есть запрос проходит без ошибки:

```go
case entity.RoleROP:
	return principal.UserID, nil
```

Итог по эндпоинтам:

| Эндпоинт | Super-admin | ROP | Что реально может ROP |
| --- | --- | --- | --- |
| `POST /v1/amocrm/configs` | ✅ | ✅ | Создать себе подключение к любому домену AmoCRM |
| `GET /v1/amocrm/configs` | ✅ | ✅ | Увидеть свои конфиги |
| `GET /v1/amocrm/configs/{id}` | ✅ | ✅ | Прочитать конфиг — **включая `client_secret` и токены доступа**, если они отдаются в ответе |
| `PATCH /v1/amocrm/configs/{id}` | ✅ | ✅ | Подменить домен, ключи, токены, признак активности |
| `DELETE /v1/amocrm/configs/{id}` | ✅ | ✅ | Удалить подключение и обезглавить свою интеграцию |

**Фронтенд — доступ ROP закрыт.**

В `project/admin/src/sections/users/user-list-view.tsx` кнопка появляется только при условии:

```
canManageAmoCrm = currentRole === 'superadmin' && targetRole === 'rop'
```

То есть **защита реализована только на уровне интерфейса**, а на уровне API её нет. Это классическая ситуация «спрятали кнопку вместо того, чтобы закрыть доступ».

### Главный аргумент, что это дефект, а не замысел

Соседний модуль — **подключение OnlinePBX — закрыт правильно.** В `project/back/internal/usecase/onlinepbx/service.go` у каждого метода работы с конфигом стоит явная проверка (строки 479, 510, 707, 730, 742, 752, 778):

```go
if principal.Role != entity.RoleSuperAdmin {
	return ErrForbidden
}
```

Две интеграции, одна и та же задача, **разный уровень защиты**. Похоже не на осознанное решение, а на пропущенную проверку в модуле AmoCRM.

Причина, по которой это вообще стало возможным: в проекте **нет единого механизма проверки прав**. Роль проверяется вручную внутри каждого метода бизнес-логики. Один забытый `if` — и эндпоинт открыт. Это системная проблема, Q-01 — её первое найденное проявление.

### Чем это грозит, если это дефект

1. **Подмена CRM.** ROP может переключить своё подключение на чужой или подставной аккаунт AmoCRM. Куда после этого уедут данные клиентов и откуда приедут лиды — вопрос открытый.
2. **Утечка ключей.** Если `client_secret` и токены доступа возвращаются в ответе `GET`, ROP получает полный доступ к CRM своей компании в обход Operator AI — то есть может делать с CRM что угодно от имени интеграции. Нужно отдельно проверить, маскируются ли секреты в ответе (пункт 2 плана проверки).
3. **Самострел.** ROP может случайно удалить подключение и остановить работу всего своего отдела — при этом Super-admin об этом не узнает.
4. **Расхождение с ТЗ.** Матрица прав в ТЗ утверждает обратное. Пока вопрос не решён, **непонятно, какой результат считать правильным при тестировании** — а значит, нельзя написать ни один тест на права доступа к этому модулю.

### Вопросы, на которые нужен ответ

1. **Задумано ли, что ROP управляет своим подключением к AmoCRM самостоятельно?**
   - Если **да** — нужно обновить ТЗ (матрицу прав в разделе 3.5) и объяснить, почему для OnlinePBX правило другое. И тогда отдельно решить: показывать ли ROP кнопку в интерфейсе, или он должен пользоваться API.
   - Если **нет** — это дефект прав доступа, заводим баг: добавить проверку `RoleSuperAdmin` в методы работы с конфигом AmoCRM, по образцу модуля OnlinePBX.
2. **Должен ли ROP вообще видеть секреты (`client_secret`, `access_token`, `refresh_token`) своего подключения?** Даже если управление ему разрешено — отдавать секреты в открытом виде необязательно.
3. **Планируется ли сделать единый механизм проверки прав** вместо ручных проверок в каждом методе? От этого зависит объём тестов на права доступа: при ручных проверках нужно тестировать **каждый эндпоинт отдельно**, автоматически ничего не гарантировано.

### Как проверить (план для QA после ответа)

1. Войти под ROP → получить токен доступа.
2. Отправить напрямую `GET /v1/amocrm/configs` с этим токеном → зафиксировать, приходят ли секреты в открытом виде.
3. Отправить `PATCH /v1/amocrm/configs/{id}` со сменой домена → зафиксировать код ответа. Ожидаемый по ТЗ — `403 Forbidden`. Фактический по коду — `200 OK`.
4. Отправить `DELETE /v1/amocrm/configs/{id}` → зафиксировать код ответа.
5. Для сравнения повторить то же самое с `/v1/onlinepbx/configs` → там ожидается `403` (эталонное поведение).
6. Проверить, может ли ROP подставить в запрос **чужой** `rop_id` при создании конфига (по коду не должен — подставляется собственный id, но проверить обязательно).

> ⚠️ Все проверки выполнять **только на тестовом окружении**, с тестовым аккаунтом AmoCRM. Не трогать реальные подключения клиентов.

## Q-02. Что должно происходить с лидом после исчерпания попыток дозвона?

**Кому:** продакт · **Важность:** высокая · **Статус:** 🔴 Открыт · **Связано с:** Д-01

### Что на диаграмме
От статуса «Ko'tarmadi» идёт ветка `4/4 muvaffaqiyatsiz` (4 из 4 неудачно) в отдельный статус **«Sifatsiz»** (некачественный лид). Есть отдельная сноска: *«Belgilangan retry muvaffaqiyatsiz bo'lsa, alohida statusga "Sifatsiz"»* — «если назначенные повторы неудачны, в отдельный статус "Sifatsiz"».

### Что в коде
Понятия «Sifatsiz» нет: ни класса статуса, ни перехода. Лид, исчерпавший лимит попыток (по умолчанию 4), **остаётся в статусе «Ko'tarmadi»** и просто перестаёт попадать в очередь обзвона. Никакого события, отметки или уведомления при этом не происходит.

Если статус с таким названием заведён у клиента в AmoCRM, он попадёт в класс «прочие» и тоже никогда не будет обзваниваться — но перевести в него лида может только человек вручную.

### Вопрос
1. **Какое поведение считается правильным** — автоматический перевод в «Sifatsiz» или сознательное решение оставить лид в «Ko'tarmadi»?
2. Если автоматический перевод нужен: откуда система должна узнать, **какой именно статус клиента** является «Sifatsiz» — по ключевому слову в названии (как остальные), или ROP должен указать его явно в настройках?
3. Должен ли ROP как-то **узнавать**, что лиды «отвалились»? Сейчас это происходит бесшумно: лид просто исчезает из работы, отчёта нет.

### Почему это важно для бизнеса и QA
«Sifatsiz» — это способ отделить мусорные заявки от рабочих. Без него в воронке накапливаются лиды в статусе «не взял трубку», которые внешне выглядят активными, но по факту мертвы. Руководитель не видит разницы между «ещё дозвонимся» и «уже никогда».

Для QA: пока нет ответа, невозможно проверить сценарий «что происходит после 4-й неудачной попытки» — неизвестен ожидаемый результат.

## Q-03. Должен ли статус лида меняться автоматически, если AI не заполнил обязательные поля?

**Кому:** продакт · **Важность:** высокая · **Статус:** 🔴 Открыт · **Связано с:** Д-02

### Что на диаграмме
После блока «Suhbat va AI tahlil» (разговор и AI-анализ) стоит развилка **`Majburiy fieldlar to'liqmi?`** («обязательные поля заполнены полностью?»). Ветка **«Yo'q»** (нет) ведёт в статус **«Chala gaplashdi»** («недоговорил»).

### Что в коде
Проверка заполненности есть, но она **не меняет статус лида**. Результат разговора помечается как `status = incomplete`, заполняется список `missing_required_fields`, и оператору в модалке подтверждения подсвечиваются незаполненные поля.

Какой статус будет у лида — решает **предложение AI и выбор оператора**, а не полнота полей.

### Вопрос
1. **Какое поведение правильное:** автоматически ставить «Chala gaplashdi» при незаполненных обязательных полях, или оставлять решение за оператором (текущее поведение)?
2. Если автоматически — **что важнее при конфликте?** Пример: AI уверенно определил статус «Uchrashuv vaqti» (клиент назначил встречу), но не смог заполнить обязательное поле «Filial». Ставим «Chala gaplashdi» и теряем информацию о встрече, или сохраняем статус AI и просто помечаем неполноту?
3. Может ли оператор подтвердить результат, **не заполнив** обязательные поля? (Сейчас — да, отправка не блокируется.)

### Почему это важно
Это развилка между «система страхует оператора» и «система доверяет оператору». От неё зависит целый пласт тест-кейсов: блокирующая валидация или предупреждающая.

Дополнительный риск: если отправка не блокируется, через 20 секунд бездействия сработает **автосинхронизация**, и в AmoCRM уедет заведомо неполная карточка — без участия человека.

## Q-04. Что должно происходить при переносе времени визита?

**Кому:** продакт · **Важность:** высокая · **Статус:** 🔴 Открыт · **Связано с:** Д-16

### Что на диаграмме
Отдельная сноска: *«Kelish vaqti o'zgarsa, unda bitta orqaga yani markazga kelish vaqtiga o'tadi, agar u ertangi yoki undan keyingi kunlar bo'lsa, agar bugun bo'lib vaqti o'zgarsa, eski flow qaytariladi»* — «если время прихода изменилось, лид откатывается на шаг назад, ко времени прихода в центр; если это завтра или позже — так; если сегодня и время изменилось — возвращается старый поток».

То есть предполагается **откат лида назад по цепочке статусов** при переносе договорённости.

### Что в коде
Логики отката нет. Поля `arrival_at` и `appointment_at` просто перезаписываются при следующей синхронизации из AmoCRM, статус при этом не меняется.

Побочный эффект: лид, уже переведённый автоматически в «Bugun keladi», при переносе визита на следующую неделю **останется в «Bugun keladi»** и продолжит выдаваться операторам как срочный.

### Вопрос
1. **Какое поведение правильное** при переносе времени визита — откат статуса назад или сохранение текущего?
2. Различается ли поведение, если новое время **сегодня** и если **в другой день**?
3. Кто инициирует перенос — оператор в разговоре, или изменение прилетает из AmoCRM (менеджер поправил карточку)? От этого зависит, где реализовывать логику.

### Почему это важно
Прямое влияние на работу операторов: лид с перенесённым визитом продолжает считаться «горячим» и занимать первое место в очереди. Оператор звонит человеку, который придёт только через неделю.

## Q-05. Что происходит с лидом после визита в центр?

**Кому:** продакт · **Важность:** средняя · **Статус:** 🔴 Открыт · **Связано с:** Д-03

### Что на диаграмме
От «Markazga keldi» (пришёл в центр) идут две ветки:
- **«To'ladi»** (оплатил) → «Yakuniy holat» (финальное состояние);
- **«To'lamadi»** (не оплатил) → «Keyingi qo'ng'iroq vaqti», со сноской *«AmoCRM da vaqt belgilanadi»* (время назначается в AmoCRM).

# Q-10. Контракт с AmoCRM: где зафиксированы ключевые слова статусов и названия полей, и кто отвечает за их неизменность?

**Кому:** продакт + разработчик BE + тот, кто занимается подключением клиентов (внедрение)
**Важность:** 🔥🔥 критическая — влияет на работоспособность продукта у каждого клиента
**Статус:** 🔴 Открыт · **Связано с:** Д-05, разделы 2 и 7 файла `02-lead-status-glossary.md`

## Суть простыми словами

Operator AI не хранит собственный справочник статусов и полей. Он **читает названия, которые клиент придумал у себя в AmoCRM, и пытается угадать их смысл по словам внутри названия**.

Аналогия: представьте переводчика, который не знает языка, но выучил 7 слов. Пока собеседник использует эти слова — всё работает. Стоит сказать то же самое другими словами — переводчик молча кивает и ничего не переводит.

Проблема в том, что **этот список слов нигде не зафиксирован как договорённость с клиентом**. Он существует только внутри кода, в одном файле.

## Что именно зашито в код

### 1. Ключевые слова статусов
Файл: `project/back/internal/usecase/calling/status_class.go`, функция `classifyStatusName`. Поиск **по вхождению** в название (регистр не важен, апострофы игнорируются):

| Ключевое слово | Во что превращается | Что будет, если слова нет |
| --- | --- | --- |
| `kotarmadi` | Не взял трубку | лид не обзванивается |
| `chala` | Недоговорили | лид не обзванивается |
| `keyingi` + `qongiroq` (оба) | Перезвонить в назначенное время | лид не обзванивается |
| `bugun` | Придёт сегодня | лид не обзванивается |
| `uchrashuv` | Встреча назначена | не будет автоперевода в «Bugun keladi» |
| `markaz` | Пришёл в центр | — |
| `yangi` | Новый | лид не обзванивается |

### 2. Названия полей с датами
Файл: `project/back/internal/usecase/amocrm/service.go:1892-1893`. Здесь совпадение **точное**, а не по вхождению:

| Название поля в AmoCRM | Для чего используется | Что будет при другом названии |
| --- | --- | --- |
| **`call vaqti`** | Время визита клиента → «звонить за час до» | Правило «за час до визита» отключается, лид становится доступен просто с начала рабочего дня |

## Почему это критично

**Всё ломается молча.** Ни одного сообщения об ошибке, ни записи в логе, ни предупреждения в интерфейсе. Со стороны ROP это выглядит так: *«у операторов пустая очередь»* или *«лиды почему-то не звонятся»* — без единой подсказки о причине.

**Сломать может кто угодно и когда угодно.** Менеджер клиента переименовал этап воронки в AmoCRM с «Ko'tarmadi» на «Недозвон» — и в этот момент обзвон этой категории лидов остановился навсегда. В AmoCRM это выглядит как безобидная косметическая правка.

**Есть ловушки на ровном месте:**
- «Markazga **kelmadi**» (*не* пришёл) содержит `markaz` → система считает, что клиент пришёл;
- «Yangi lid — bugun keladi» будет распознан как «Bugun keladi», потому что `bugun` проверяется раньше `yangi`;
- поле «Kelish vaqti» вместо «call vaqti» — не найдено, хотя по смыслу это одно и то же.

# Q-11. Каков статус двух параметров «Mezonlar», которые сохраняются, но не влияют на очередь?

**Кому:** продакт + разработчик BE
**Важность:** высокая · **Статус:** 🔴 Открыт · **Связано с:** Д-11, Д-12 (файл `02-lead-status-glossary.md`, раздел 12)

> **Важно:** это наблюдение **по чтению кода**, на живом стенде пока не воспроизводилось. Вопрос задаётся именно как уточнение статуса функциональности, а не как заявка о дефекте — вполне возможно, что работа над этими параметрами ещё не завершена.

## Суть

На экране «Mezonlar» ROP настраивает 8 параметров очереди обзвона. Шесть из них участвуют в логике выбора лидов. Два — **сохраняются в базу и возвращаются в интерфейс, но в правилах очереди не используются**.

## Что именно

### 1. `work_end` — конец рабочего дня (по умолчанию 20:00)

**Ожидаемое поведение по смыслу параметра:** после указанного часа очередь перестаёт выдавать лидов операторам.

**Что видно в коде:** в SQL-запросе выборки лидов (`ClaimNextLeadForOperator`, `db/query/queries/calling.sql`) участвует только `work_start` — как момент, с которого становятся доступны лиды «Bugun keladi» без указанного времени визита. Условия, ограничивающего выдачу сверху, в запросе нет.

Параметр валидируется при сохранении (`settings.go:152` — проверяется, что конец позже начала), сохраняется в `rop_call_settings.work_end`, отдаётся в ответе `GET /v1/calling/settings` в блоке `effective`. В формировании правил очереди (`queueRulesForROP`, `queue_rules.go`) не участвует.

**Следствие, если поведение именно такое:** ROP выставляет конец рабочего дня 18:00, но в 23:00 очередь продолжает выдавать лидов на обзвон.

### 2. `default_call_time` — время звонка по умолчанию (по умолчанию 09:00)

**Замысел виден из комментария в самом коде** (`internal/usecase/calling/settings.go:24`):
```go
defaultDefaultCallTime = "09:00" // day-only agreements ("dushanba deng") call at this hour
```
То есть: клиент сказал «перезвоните в понедельник», не назвав часа → звоним в понедельник в 09:00.

**Что видно в коде:** значение сохраняется, резолвится в `EffectiveCallSettings.DefaultCallTime`, отдаётся в API. Поиск по всему бэкенду показывает, что за пределами файла настроек и слоя хранения оно **нигде не читается** — ни в правилах очереди, ни при планировании времени следующего звонка.

**Следствие, если поведение именно такое:** договорённость «в понедельник» без указания часа не превращается в конкретное время звонка. При этом для статуса «Keyingi qo'ng'iroq vaqti» время перезвона **обязательно** — без него лид выпадает из очереди (см. `02-lead-status-glossary.md`, раздел 3.2). То есть параметр задумывался как страховка ровно от этой ситуации.

## Вопросы

1. **Каков статус этих двух параметров** — функциональность в разработке, отложена, или отменена, а поля остались от предыдущей версии замысла?
2. Если работа **не завершена** — стоит ли пока скрыть их на экране «Mezonlar»? Сейчас ROP видит настройки, меняет их и ожидает эффекта.
3. Если функциональность **отменена** — правильно ли будет удалить параметры из интерфейса и API, чтобы не вводить в заблуждение?
4. По `work_end` отдельно: **должна ли очередь вообще ограничиваться рабочим временем?** Возможно, замысел был другим — например, ограничивать не выдачу лидов, а что-то ещё (учёт смен, отчётность).
5. По `default_call_time` отдельно: **как сейчас должен поступать оператор**, если клиент назвал день без времени? Ставить час самому, или для этого есть другое соглашение?

# Q-12. Новый модуль тарифов: ограничивает ли тариф доступ к функциям?

**Кому:** продакт + разработчик BE
**Важность:** высокая — это потенциально механизм разграничения доступа, а значит зона тестирования прав
**Статус:** 🔴 Открыт · **Дата обнаружения:** 23.07.2026 (появилось в коммитах 21–22.07)

## Что добавили

В систему добавили модуль **тарифных планов**. Их ровно три, с фиксированными кодами:
- `taxlil_dashboard` — «аналитический дашборд»;
- `taxlil_dashboard_auto_call` — «дашборд + автообзвон»;
- `full_ai` — «полный AI».

Что появилось в коде:
- таблица `plans` и три плана;
- публичный `GET /v1/plans` — используется на лендинге в блоке цен;
- `PUT /v1/plans/{code}` — **только super_admin**, редактирует лишь витрину (название, цену, описание, список фич);
- у пользователя (ROP) появилось поле `users.tariff`;
- у заявок с лендинга появились поля `tariff` и `converted_at` (когда заявку сконвертировали в клиента);
- на лендинге в форме демо-заявки появился **необязательный** выбор тарифа;
- в админке — экран `/dashboard/plans` для super_admin.

## В чём вопрос

По коду видно, что тариф **сейчас нигде не ограничивает функциональность**. Поиск показал: `users.tariff` записывается при создании ROP и хранится, но **ни один модуль** (очередь звонков, AI, AmoCRM, OnlinePBX) не проверяет тариф перед тем, как дать доступ к функции. То есть на данный момент тариф — это:
- витрина цен на лендинге;
- атрибут клиента (просто записан);
- то, что редактирует super_admin.

Но сами названия планов намекают на разграничение: `taxlil_dashboard` (только дашборд) vs `taxlil_dashboard_auto_call` (+ автообзвон) vs `full_ai` (всё). Это выглядит как **будущий механизм ограничения доступа**.

## Вопросы

1. **Должен ли тариф ограничивать доступ к функциям?** Например: ROP на тарифе `taxlil_dashboard` **не должен** иметь автообзвона, а на `full_ai` — должен всё.
2. Если да — **это ещё не реализовано** (проверок в коде нет). Тогда: это в разработке, и нам готовить тест-кейсы заранее? Какой тариф что открывает — есть матрица «тариф × функция»?
3. Если нет (тариф — только для биллинга и маркетинга) — тогда он не входит в тестирование прав, и мы просто фиксируем это.
4. **Кто и когда назначает тариф ROP?** При создании super_admin'ом? Меняется ли потом?
5. **Контроль enum на лендинге.** Значение тарифа в форме демо-заявки должно **точно** совпадать с backend-enum (в коде это прямо прокомментировано). Кто следит, что значения на лендинге и на бэкенде не разойдутся? (тот же класс проблемы, что и Q-10 — контракт по строковым значениям).

## Влияние на QA

- Если тариф **будет** гейтить функции — это раздел тестирования прав доступа, сопоставимый по важности с ролями. Понадобится матрица «тариф × функция × роль», и это кандидат на автоматизацию.
- Если **нет** — вычёркиваем из тест-плана, оставляем только смоук: тариф сохраняется, отображается, редактируется super_admin'ом.
- В обоих случаях: проверить, что `PUT /v1/plans/{code}` **недоступен** роли ROP и оператору (по коду — только super_admin, но проверить, как Q-01).
