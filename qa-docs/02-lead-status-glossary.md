# 02. Глоссарий статусов лида и правила переходов

**Дата составления:** 21.07.2026
**Источник истины:** код бэкенда (`project/back/internal/usecase/calling/`, `db/query/queries/calling.sql`, `internal/usecase/amocrm/service.go`)
**Сверено с:** `docs/lead-life-cycle.png` — расхождения вынесены в раздел 12 отдельным списком

---

## 1. Как читать этот документ

**Лид** — потенциальный клиент. В AmoCRM это называется «сделка», в нашей системе — «лид». Это одно и то же.

**Статус лида** — этап, на котором сейчас находится работа с клиентом. Аналогия: как статус посылки — «принята», «в пути», «доставлена». Только здесь этапы про переговоры: «новый», «не взял трубку», «договорились о встрече».

**Очередь обзвона** — список лидов, которых система готова выдать оператору прямо сейчас. Аналогия: электронная очередь в банке, только талоны раздаёт не человек, а правила.

---

## 2. Главное, что нужно понять про статусы

Это самое важное место документа. Если понять его неправильно — все тесты будут написаны не про то.

### Статусы **не являются** фиксированным списком в нашей системе

В коде нет справочника статусов. Нет enum, нет таблицы «допустимые статусы», нет проверки «такого статуса не существует».

**Статусы приходят из AmoCRM каждого клиента и являются произвольным текстом.** Клиент А назвал этап «Ko'tarmadi», клиент Б — «КО'ТАРМАДИ», клиент В — «Ko'tarmadi (2-urinish)». Для AmoCRM это три разных названия.

### Как система понимает, что это за статус

Система **угадывает смысл статуса по его названию** — ищет ключевое слово внутри строки.

Аналогия: представьте сортировщика на почте, который не знает индексов и раскладывает конверты по надписям: если в адресе встречается слово «Ташкент» — в левый ящик, «Самарканд» — в правый. Если написано что-то незнакомое — в ящик «прочее», который никуда не отправляется.

Механизм (`internal/usecase/calling/status_class.go`, функция `classifyStatusName`):

1. Название приводится к нижнему регистру;
2. Удаляются все виды апострофов (`'`, `’`, `` ` ``, `ʻ`, `ʼ`) — поэтому `Ko'tarmadi`, `Ko’tarmadi` и `Kotarmadi` для системы одно и то же;
3. Лишние пробелы схлопываются;
4. В получившейся строке ищется ключевое слово **по вхождению** (не по точному совпадению).

### Восемь «классов» статусов

Внутренние коды из `status_class.go` — это то, чем система оперирует на самом деле:

| Внутренний класс | Ключевое слово для распознавания |
| --- | --- |
| `StatusClassKotarmadi` | содержит `kotarmadi` |
| `StatusClassChala` | содержит `chala` |
| `StatusClassKeyingiQongiroq` | содержит `keyingi` **и** `qongiroq` (оба слова) |
| `StatusClassBugunKeladi` | содержит `bugun` |
| `StatusClassUchrashuv` | содержит `uchrashuv` |
| `StatusClassMarkazgaKeldi` | содержит `markaz` |
| `StatusClassYangi` | содержит `yangi` |
| `StatusClassOther` | **всё остальное** |

### ⚠️ Три следствия, критичных для тестирования

**Следствие 1. Порядок проверки имеет значение.** Условия проверяются сверху вниз в порядке из таблицы, и **побеждает первое совпадение**. Статус с названием «Yangi lid — bugun keladi» будет распознан как **Bugun keladi**, потому что `bugun` проверяется раньше, чем `yangi`. Отличный кандидат на негативный тест.

**Следствие 2. Незнакомый статус = лид никогда не будет обзвонен.** Класс `Other` **никогда не попадает в очередь**. Это сделано намеренно и прокомментировано в коде: *«лучше пропустить неправильно названный статус, чем автоматически обзванивать лидов по непонятным правилам»*. Безопасно — но **молча**. ROP переименовал этап в AmoCRM с «Ko'tarmadi» на «Трубку не взял» → все такие лиды бесшумно выпали из обзвона, и никто нигде не увидит предупреждения.

**Следствие 3. Ложное срабатывание по подстроке.** Статус «Markazga kelmadi» (**не** пришёл в центр) содержит `markaz` → будет распознан как «Markazga keldi» (пришёл в центр), то есть как успешный визит. Смысл противоположный. Проверить обязательно.

## 3. Глоссарий: узбекский → русский → смысл

Порядок — по приоритету в очереди обзвона (кого система выдаёт первым).

### 3.1 «Bugun keladi» — приоритет 1

| | |
| --- | --- |
| **Узбекский термин** | Bugun keladi |
| **Дословный перевод** | «Сегодня придёт» |
| **Рабочий перевод** | Клиент придёт сегодня |
| **Внутренний класс** | `StatusClassBugunKeladi` (`bugun_keladi`) |
| **Распознаётся по** | слову `bugun` в названии |

**Смысл:** клиент подтвердил, что придёт в офис/центр сегодня. Самый «горячий» тип лида — до его визита осталось немного, надо позвонить и напомнить.

**Когда лид попадает в этот статус:**
- оператор поставил вручную (в разговоре клиент сказал «сегодня приду» — на диаграмме ветка *«Bugun kelaman dedi»*);
- **автоматически** — фоновый процесс переводит сюда лидов из «Uchrashuv vaqti», когда наступил день встречи (см. раздел 6).

**Условие попадания в очередь** (SQL `ClaimNextLeadForOperator`):
```
NOW() >= arrival_at − before_arrival_min
```
где `arrival_at` — время визита клиента, `before_arrival_min` — 60 минут по умолчанию.

То есть: клиент записан на 15:00 → лид становится доступен для звонка в 14:00.

**Если время визита не заполнено** (`arrival_at` пустое) — лид становится доступен с **начала рабочего дня** (`work_start`, по умолчанию 08:00).

**Куда переходит дальше:** зависит от результата разговора — в любой другой статус. Автоматических переходов из «Bugun keladi» в коде нет.

---

### 3.2 «Keyingi qo'ng'iroq vaqti» — приоритет 2

| | |
| --- | --- |
| **Узбекский термин** | Keyingi qo'ng'iroq vaqti |
| **Дословный перевод** | «Время следующего звонка» |
| **Рабочий перевод** | Назначен перезвон на конкретное время |
| **Внутренний класс** | `StatusClassKeyingiQongiroq` (`keyingi_qongiroq`) |
| **Распознаётся по** | наличию **обоих** слов: `keyingi` и `qongiroq` |

**Смысл:** клиент взял трубку и попросил перезвонить в конкретное время («перезвоните завтра после обеда»). Договорённость есть, время известно.

**Когда лид попадает в этот статус:** оператор (или AI) ставит его после разговора, одновременно указывая время следующего звонка.

**Условие попадания в очередь:**
```
next_call_at IS NOT NULL   И   next_call_at <= NOW()
```

⚠️ **Важная ловушка:** если статус поставили, но **время перезвона не заполнили** — лид **навсегда выпадает из очереди**. Условие требует, чтобы `next_call_at` был заполнен, а второе общее условие очереди (`next_call_at IS NULL OR next_call_at <= NOW()`) такой лид пропустит, но первое — нет. Никакого «значения по умолчанию» здесь не применяется. Обязательный негативный тест.

**Откуда берётся время перезвона:** **только из того, что передал оператор** при подтверждении (поле `next_call_at` в запросе `confirm` / `confirm-manual`). Сервер сам это время **не вычисляет** — не выводит из статуса, не парсит из текста разговора.

**Куда переходит дальше:** любой статус по результату следующего разговора.

### 3.3 «Chala gaplashdi» — приоритет 3

| | |
| --- | --- |
| **Узбекский термин** | Chala gaplashdi |
| **Дословный перевод** | «Недоговорил», «поговорил наполовину» |
| **Рабочий перевод** | Разговор не завершён |
| **Внутренний класс** | `StatusClassChala` (`chala`) |
| **Распознаётся по** | слову `chala` |

**Смысл:** трубку взяли, разговор начался, но не довели до конца — связь оборвалась, клиент был занят, не успели выяснить всё нужное. Договорённости о времени нет.

**Когда лид попадает в этот статус:** ставит оператор или предлагает AI. По диаграмме сюда же должен попадать лид, у которого AI не смог заполнить обязательные поля — **в коде такого автоматического перехода нет** (см. расхождение Д-04).

**Условие попадания в очередь:**
```
last_call_at + chala_delay_min <= NOW()
```
где `chala_delay_min` — 60 минут по умолчанию.

То есть: разговор оборвался в 11:00 → лид вернётся в очередь в 12:00.

Если звонков ещё не было (`last_call_at` пустое) — доступен сразу.

**Ограничения по количеству попыток нет** — в отличие от «Ko'tarmadi», лид в этом статусе может возвращаться в очередь бесконечно, каждый час.

### 3.4 «Ko'tarmadi» — приоритет 4

| | |
| --- | --- |
| **Узбекский термин** | Ko'tarmadi |
| **Дословный перевод** | «Не поднял» (трубку) |
| **Рабочий перевод** | Не берёт трубку |
| **Внутренний класс** | `StatusClassKotarmadi` (`kotarmadi`) |
| **Распознаётся по** | слову `kotarmadi` (после удаления апострофов) |

**Смысл:** дозвониться не удалось. Единственный статус, где действует **лимит попыток**.

**Когда лид попадает в этот статус:**
- оператор ставит вручную;
- интерфейс **предзаполняет** этот статус автоматически, если дозвон не удался. Фронтенд ищет в списке статусов первый подходящий по шаблону `/ko.{0,2}tarma/i` (`src/sections/calling/calling-modal.tsx:36`). Предзаполнение ≠ сохранение: оператор всё равно подтверждает.

**Условие попадания в очередь** — **два** условия одновременно:
```
attempts_count < max_attempts          (по умолчанию 4)
last_call_at + retry_interval_min <= NOW()   (по умолчанию 180 минут = 3 часа)
```

**Как считаются попытки:**
- счётчик `attempts_count` увеличивается на 1 **при каждом подтверждении звонка** (`RecordLeadCallAttempt`) — независимо от того, взяли трубку или нет;
- счётчик **пожизненный, а не суточный**. Поле `attempts_date` в базе есть, но используется только для статистики, в правилах очереди не участвует;
- **сбрасывается в 0 только при смене статуса в AmoCRM** (`ResetLeadAttemptsOnStatusChange`) — то есть если кто-то вручную перевёл лид в другой статус, бюджет попыток восстанавливается.

**Что происходит после 4 попыток:** лид просто **перестаёт попадать в очередь**. Молча. Статус остаётся «Ko'tarmadi», лид никуда не переходит.

⚠️ По диаграмме здесь должен появляться статус **«Sifatsiz»** — в коде такого перехода **нет** (см. расхождение Д-01, самое важное в документе).

### 3.5 «Yangi lid» — приоритет 5

| | |
| --- | --- |
| **Узбекский термин** | Yangi lid |
| **Дословный перевод** | «Новый лид» |
| **Рабочий перевод** | Новый, ещё не обработанный |
| **Внутренний класс** | `StatusClassYangi` (`yangi`) |
| **Распознаётся по** | слову `yangi` |

**Смысл:** лид только что приехал из AmoCRM, с ним ещё никто не работал.

**Когда лид попадает в этот статус:** приходит из AmoCRM при фоновой синхронизации (раз в 2 минуты) или по вебхуку. Синхронизируются только воронки, **на которые назначен хотя бы один оператор**.

**Условие попадания в очередь:** никаких дополнительных условий — доступен **сразу**.

**Приоритет самый низкий.** Логика бизнеса: сначала выполняем обещания уже знакомым клиентам, потом берём новых.

## 4. Сводная таблица приоритетов

Когда оператор жмёт «дать следующего лида», система сортирует всех доступных так:

| Приоритет | Класс | Условие доступности | Лимит попыток |
| --- | --- | --- | --- |
| 1 | Bugun keladi | за `before_arrival_min` до визита (60 мин) или с `work_start` (08:00) | нет |
| 2 | Keyingi qo'ng'iroq vaqti | наступило `next_call_at` | нет |
| 3 | Chala gaplashdi | прошло `chala_delay_min` после звонка (60 мин) | нет |
| 4 | Ko'tarmadi | прошло `retry_interval_min` (180 мин) **и** попыток < 4 | **4** |
| 5 | Yangi lid | сразу | нет |
| — | Uchrashuv vaqti | никогда | — |
| — | Markazga keldi | никогда | — |
| — | Прочие | никогда | — |

**При равном приоритете** сортировка идёт по времени готовности (кто дольше ждёт — тот первый), при равенстве — по дате создания лида.

**Общие условия для всех классов** (действуют поверх таблицы):
- лид не удалён (`is_deleted = FALSE`);
- статус в AmoCRM не «успешно реализовано» (142) и не «закрыто и не реализовано» (143);
- лид не заблокирован другим оператором;
- `next_call_at` пустое ИЛИ уже наступило — то есть **отложенный лид не выдаётся, в каком бы статусе он ни был**;
- воронка лида назначена этому оператору.

## 5. Параметры настройки («Mezonlar»)

Настраиваются ROP на экране `/dashboard/mezonlar`, хранятся в `rop_call_settings`. Пустое значение в базе = используется значение по умолчанию из кода.

| Параметр | По умолчанию | На что влияет | Работает? |
| --- | --- | --- | --- |
| `work_start` | 08:00 | С какого часа доступны «Bugun keladi» без указанного времени визита | ✅ |
| `work_end` | 20:00 | — | ❌ **В логике очереди не используется** (см. Д-08) |
| `retry_interval_min` | 180 мин | Пауза между попытками для «Ko'tarmadi» | ✅ |
| `max_attempts` | 4 | Лимит попыток для «Ko'tarmadi» | ✅ |
| `before_arrival_min` | 60 мин | За сколько до визита звонить «Bugun keladi» | ✅ |
| `chala_delay_min` | 60 мин | Пауза перед возвратом «Chala gaplashdi» | ✅ |
| `default_call_time` | 09:00 | Задумано: час звонка при договорённости «в понедельник» без времени | ❌ **Нигде не используется** (см. Д-08) |
| `bugun_transition_time` | 00:00 | Час перевода «Uchrashuv» → «Bugun keladi» | ✅ |

**Не настраиваются (зашиты в код):**

| Параметр | Значение | Где |
| --- | --- | --- |
| Блокировка лида за оператором | **5 минут** | `lockLease`, `service.go:22` |
| Отсрочка при «пропустить» | **30 минут** | `skipDelay`, `service.go:23` |
| Обратный отсчёт до автонабора | **10 секунд** | фронтенд |
| Автосинхронизация после звонка | **20 секунд** | `AUTO_SYNC_SECONDS`, фронтенд |
| Часовой пояс всех правил | **Asia/Tashkent** | `businessTimezone`, `queue_rules.go:14` |

⚠️ Изменение настроек **не пересчитывает уже назначенные времена**. Комментарий в коде: *«Changes apply from the next queue computation on — already-scheduled next_call_at values are not recalculated»*.

## 6. Единственный автоматический переход статуса

Во всей системе автоматически меняется **один** статус: **Uchrashuv vaqti → Bugun keladi**.

**Как работает** (`internal/usecase/calling/transitions.go`):

1. Фоновый процесс запускается **каждые 5 минут** (жёстко, не настраивается);
2. Проходит по всем ROP, **у которых есть операторы, назначенные на воронки** (у остальных не работает вовсе);
3. Проверяет: наступил ли час `bugun_transition_time` (по умолчанию 00:00);
4. Выбирает лидов, у которых статус класса `Uchrashuv` **и** `appointment_at` раньше конца сегодняшнего дня;
5. Переводит каждого в статус класса `Bugun keladi` **той же воронки** и отправляет изменение в AmoCRM.

**Ограничения, важные для тестирования:**
- за один проход обрабатывается **не более 200 лидов** (`LIMIT 200` в `ListAppointmentLeadsDue`). При большем объёме остальные подождут следующего прохода;
- если в воронке **нет статуса со словом `bugun`** — лид остаётся на месте, ошибки не будет, в логе тоже ничего;
- если `appointment_at` не заполнено — переход не сработает;
- операция идемпотентна: после перехода лид больше не подходит под условие выборки.

## 7. Откуда система берёт даты визита и встречи

Критично для тестирования и **нигде не задокументировано**.

Два поля с датами берутся из **кастомных полей AmoCRM, найденных по названию**:

| Поле в базе | Название кастомного поля в AmoCRM | Используется для |
| --- | --- | --- |
| `arrival_at` | **`call vaqti`** | «Bugun keladi»: за сколько звонить до визита |
| `appointment_at` | **`uchrashuv vaqti`** | «Uchrashuv»: когда переводить в «Bugun keladi» |

Код: `internal/usecase/amocrm/service.go:1892-1893`.

Сопоставление идёт по **точному совпадению** названия после нормализации (нижний регистр, удаление апострофов, схлопывание пробелов) — функция `normalizeCustomFieldName`. Это **не поиск по вхождению**, в отличие от статусов.

⚠️ **Следствие:** если ROP назвал поле «Kelish vaqti» или «Время визита» — оно **не будет найдено**, дата останется пустой, и вся логика «звонить за час до визита» тихо перестанет работать. Ошибки не будет.

Поддерживаемые форматы значения: Unix-время (числом или строкой) и RFC3339. Другие форматы игнорируются.

## 9. Жизненный цикл одного звонка (состояния сессии)

Отдельная сущность — не путать со статусом лида. Статус лида живёт в AmoCRM, состояние сессии — только у нас, описывает одну попытку дозвона.

```
guideline  → оператору показали инструктаж перед звонком
   ↓
dialing    → идёт набор номера
   ↓
in_call    → разговор идёт
   ↓
wrap_up    → звонок кончился, ждём AI-анализ
   ↓
confirmed / synced   → оператор подтвердил, данные ушли в AmoCRM
```
Тупиковые состояния: `skipped` (пропустил), `failed` (сорвалось).

**Условие запуска AI:** звонок анализируется, **только если** известен оператор (по внутреннему номеру) **и** длительность разговора > 0. Неотвеченные звонки AI не обрабатывает вообще.

## 10. Терминальные (финальные) статусы

Единственное, что система считает «работа закончена» — два **системных** статуса AmoCRM:

| Код AmoCRM | Значение |
| --- | --- |
| `142` | Успешно реализовано |
| `143` | Закрыто и не реализовано |

Лиды в этих статусах исключаются из очереди явным условием в SQL. Никаких других «финальных» статусов система не знает — «Yakuniy holat» с диаграммы в коде отсутствует.

**[обновлено 23.07]** Появилось смежное правило (касается не очереди, а **выпадающего списка статусов при обзвоне**): из выбора оператора теперь исключаются не только 142 и 143, но и системная стадия «Неразобранное» (тип 1) — как результат звонка она бессмысленна. Код: `isSelectableStatus` в `internal/usecase/calling/session.go`. На попадание лида в очередь это не влияет; влияет на то, какой статус оператор может выбрать в модалке подтверждения.

## 11. Чек-лист: почему лид может «пропасть» из обзвона

Практическая выжимка. Все причины — молчаливые, ни одна не даёт сообщения об ошибке.

1. Название статуса не распозналось → класс `Other`;
2. Статус «Keyingi qo'ng'iroq vaqti», но время перезвона не заполнено;
3. «Ko'tarmadi» и исчерпаны 4 попытки;
4. `next_call_at` в будущем (после «пропустить» или назначенного перезвона);
5. Лид заблокирован другим оператором (до 5 минут);
6. Статус AmoCRM 142 или 143;
7. Лид помечен удалённым в AmoCRM;
8. Воронка лида не назначена ни одному оператору → лид даже не синхронизируется;
9. Статус класса `Uchrashuv` или `Markazga keldi` — по правилам вне очереди;
10. «Bugun keladi» с заполненным `arrival_at` в будущем — ждёт своего часа минус 60 минут.
