Реализованы позитивные проверки OnlinePBX extensions, редактирования и отката
тарифа, создания ROP с каждым активным тарифом, назначения нескольких воронок,
сохранения подсказок/описания и всех критериев очереди. Все изменения выполняются
последовательно, снимают исходное состояние и восстанавливают его в `finally`.

Проверка повторной синхронизации подключённой AmoCRM дважды получила конфликт
вместо успешного результата. Сценарий `UAT-SA-003` не был ослаблен: зарегистрирован
BUG-046 и добавлен строгий регрессионный guard. До исправления он считается
«заблокировано дефектом», а не ежедневным падением или успешной проверкой.

После прогона выполнен отдельный аудит cleanup: временных UAT-пользователей и
тарифов не осталось; подсказки статусов/полей, описание компании и критерии
очереди восстановлены.

## Почему осталось восемь ворот

Два Landing-сценария требуют отдельный staging Landing и удаляемый канал
demo-заявок. Production Landing не используется: он связан с production API.

Шесть Operator/flow-сценариев требуют детерминированных лидов и AI-сессий.
Существующий публичный API создаёт запись во внешней AmoCRM, но не умеет полностью
удалять локальные `lead_call_state`, попытки и call sessions. Использование общей
очереди сделало бы ежедневный результат зависимым от чужих данных и загрязняло бы
стенд. Поэтому нужен защищённый staging-only fixture API с create/reset/delete по
точному UAT-ID.

Выдача дополнительных прав существующей учётке эти восемь ворот не решает:
нужных операций очистки в текущем API нет.
