**Правило проекта:** баг заводим только после того, как воспроизвели его сами. Наблюдения по коду (ещё не воспроизведённые) живут в `03-questions-for-team.md`, а не здесь.

**Как заводить:** скопировать «Шаблон» ниже, вставить в раздел «Баги», присвоить номер (BUG-XXX), заполнить поля, добавить строку в сводную таблицу.

> ⚠️ **Все баги BUG-001…BUG-008 найдены на PRODUCTION (23.07.2026).** Это повышает срочность — дефекты видны реальным пользователям прямо сейчас. Отдельно критично: BUG-002 (открытый доступ супер-админа) находится на проде.
>
> **Два предупреждения по процессу:**
> 1. **Мы создавали/меняли данные на боевой системе.** Часть багов воспроизводилась действиями, которые мутируют прод: создание РОП (BUG-007), редактирование тарифа (BUG-008), деактивация РОП (BUG-006). > 2. **Впредь функциональные проверки (создание, редактирование, деактивация) выполняем на staging/test, а не на проде** — по правилу проекта. На проде допустимо только пассивное наблюдение (открыть страницу, посмотреть), без изменения данных.
>
> **[обновлено 25.07] ✅ Доступ к окружениям получен** — и к staging, и к production. Проблема «проверять негде» снята.
>
> **Правило с этого момента:**
>
> | Окружение | Что делаем |
> | --- | --- |
> | **staging** | Все функциональные проверки: создание, изменение, удаление, воспроизведение дефектов, автотесты |
> | **production** | **Только пассивное наблюдение.** Открыть страницу, посмотреть. Ничего не менять |
>
> Доступ к проду — это возможность разобрать инцидент и сверить поведение, **а не разрешение там тестировать**.
>
> **Два следствия для этого файла:**
>
> 1. **У всех восьми дефектов в поле «Окружение» стоит production.** Их нужно **перепроверить на staging** — часть могла быть уже починена вместе с другими работами. До перепроверки статусы остаются «Новый»;
> 2. **Долг по проду:** тестовые руководители отделов, изменённые тарифы и деактивированный пользователь, оставшиеся после июльских проверок, нужно найти и убрать. Список — в предупреждении выше.

### BUG-001. Кнопка показа пароля отображается текстом вместо иконки

| Платформа | Приложение | Окружение | Описание |
| --- | --- | --- | --- |
| Web / браузер | Admin — экран входа (до авторизации) | production | В поле «Пароль» переключатель видимости выводится словом «показать» / «ko'rsatish» вместо иконки (глаз) |

**Приоритет:** P3 (косметический, на функциональность не влияет)   **Статус:** 🔴 Новый   **Дата:** 23.07.2026

**Описание:**
На странице входа справа в поле «Пароль» находится переключатель, скрывающий/показывающий введённый пароль. Сейчас он отрисован **текстом** («показать», в узбекской локали — «ko'rsatish»). По общепринятому паттерну и по исходному дизайну шаблона там должна быть **иконка-глаз** (открытый глаз / перечёркнутый глаз), а не подпись словами.

**Шаги:**
1. Открыть страницу входа Admin (`/auth/jwt/sign-in`).
2. Посмотреть на правую часть поля «Пароль».

**Ожидаемый результат:**
В правой части поля — иконка (глаз). По клику пароль показывается/скрывается, иконка меняется (открытый ↔ перечёркнутый глаз).

**Фактический результат:**
Вместо иконки — текст «показать». После переключения, судя по коду, текст меняется на «скрыть» / «yashirish».

**Вложение:**
`Снимок экрана — 2026-07-23 в 13.40.53.png`

**Связь / где в коде:**
- `project/admin/src/auth/view/jwt/jwt-sign-in-view.tsx:125` — рендерится `{showPassword.value ? t('hide') : t('show')}` (текст) внутри `InputAdornment`, где ожидается `<Iconify>` с иконкой глаза.
- Тексты берутся из локалей: `src/locales/ru/auth.json` (`"show": "показать"`), `src/locales/uz/auth.json` (`"show": "ko'rsatish"`).
- Починка: заменить текстовые метки на иконку (например `solar:eye-bold` / `solar:eye-closed-bold`), сохранив `aria-label` для доступности.

**Заметка QA:** на скриншоте в поле «Логин» подставлено `root` — это отдельная проблема, заведена как BUG-002.

<a id="bug-002"></a>
### BUG-002. 🔒 Экран входа предзаполнен учётными данными super-admin (в т.ч. на проде)

| Платформа | Приложение | Окружение | Описание |
| --- | --- | --- | --- |
| Web / браузер | Admin — экран входа (до авторизации) | **production** (воспроизведено на прод-сайте) | При открытии страницы входа поля «Логин» и «Пароль» уже заполнены реальными дефолтными учётными данными супер-администратора (`root` / дефолтный пароль). Достаточно нажать «Войти» |

**Приоритет:** P1 — проблема безопасности   **Статус:** 🔴 Новый   **Дата:** 23.07.2026

**Описание:**
Форма входа открывается с **предзаполненными** логином и паролем. Это не пустые плейсхолдеры, а рабочие значения по умолчанию, зашитые в код фронтенда: логин `root`, пароль — дефолтный (8 символов). `root` — это учётная запись **супер-администратора**, которая автоматически создаётся бэкендом при старте. То есть любой, кто открыл страницу входа (включая продакшн), может войти под супер-админом одним кликом, ничего не зная.

Двойная проблема:
1. **Фронтенд** подставляет готовые логин/пароль в форму (в том числе на проде).
2. **Бэкенд** при старте создаёт супер-админа с этим же дефолтным паролем, и пароль, судя по всему, не был сменён.

**Шаги:**
1. Открыть прод-сайт Admin, страницу входа.
2. Не вводя ничего, посмотреть на поля «Логин» и «Пароль» — они уже заполнены.
3. (Не выполнять на проде без разрешения) Нажать «Войти».

**Ожидаемый результат:**
Поля «Логин» и «Пароль» **пустые**. Никаких учётных данных по умолчанию в форме. Дефолтный пароль супер-админа на любом окружении сменён на уникальный и хранится только в секретах (`.env`), а не в коде.

**Фактический результат:**
Поля заполнены `root` / дефолтным паролем прямо при открытии; вход под супер-админом возможен без знания пароля. Воспроизводится на продакшене.

**Вложение:**
`Снимок экрана — 2026-07-23 в 13.44.10.png`

**Связь / где в коде:**
- `project/admin/src/auth/view/jwt/jwt-sign-in-view.tsx:52-55` — `defaultValues: { username: 'root', password: '<замаскировано — см. Р-17>' }`. Должно быть пустым (`username: '', password: ''`).
- Бэкенд: при старте создаётся дефолтный супер-админ (`EnsureDefaultSuperAdmin`, `internal/app/app.go`) — необходимо убедиться, что на проде его пароль сменён.
- Ранее зафиксировано как расхождение **Р-17** и риск **R-5** в `01-project-analysis.md`.

**Заметка QA — срочность:** это не косметика. Пока предзаполнение и дефолтный пароль живы на проде, доступ супер-админа фактически открыт. Рекомендую эскалировать вне общей очереди багов и параллельно проверить: (1) сменён ли реальный пароль `root` на проде; (2) не входили ли под ним посторонние (логи входов). Проверку «можно ли реально залогиниться» на проде выполнять **только с разрешения** ответственного — не подбирать доступ к боевой системе самовольно.

### BUG-004. Поле «Телефон» принимает буквы и любой текст (нет проверки формата)

| Платформа | Приложение | Окружение | Описание |
| --- | --- | --- | --- |
| Web / браузер | Admin — Super-admin, диалог «Создать РОП» | production | Поле «Телефон» принимает произвольный текст (буквы, символы); нет проверки формата и нет маски ввода `+998 xx xxx xx xx` |

**Приоритет:** P2 (пропускает некорректные данные в систему)   **Статус:** 🔴 Новый   **Дата:** 23.07.2026

**Описание:**
В форме создания РОП поле «Телефон» не проверяет формат вводимого значения. Можно ввести буквы («выфвыфвыфвфывфвы»), пробелы, любые символы — форма это принимает. Ожидается ввод узбекского номера в формате `+998 xx xxx xx xx`, и никакие другие символы вводиться не должны (либо блокироваться маской, либо отсекаться валидацией).

**Шаги:**
1. Войти как Super-admin, открыть раздел ROP.
2. Нажать создание нового ROP → «Создать РОП».
3. В поле «Телефон» ввести буквы, например `выфвыфвыф`.
4. Заполнить остальные обязательные поля корректно и нажать «Создать».

**Ожидаемый результат:**
Поле принимает только телефон в формате `+998 xx xxx xx xx`. Буквы и посторонние символы либо не вводятся (маска), либо форма показывает ошибку валидации и не даёт создать ROP с некорректным телефоном.

**Фактический результат:**
Поле принимает любой текст, включая буквы. Валидации формата нет — проверяется только, что поле не пустое.

**Вложение:**
`Снимок экрана — 2026-07-23 в 13.48.33.png`

**Связь / где в коде:**
- `project/admin/src/sections/users/user-list-view.tsx:222` — `phone: z.string().trim().min(1, ...)`: проверка только на непустоту, без regex/маски.
- Поле рендерится обычным `Field.Text name="phone"` (строки ~1597, ~1649) — без маски ввода.
- Починка: добавить в zod-схему проверку формата (regex для `+998` + 9 цифр) и/или маску ввода на поле. Также желательно синхронно проверять формат на бэкенде (валидация на клиенте обходится через API).

**Заметка QA:**
1. Проверить то же поле «Телефон» в форме **«Создать оператора»** и в диалогах **редактирования** — валидация телефона, судя по коду, общая, дефект наверняка воспроизводится и там.
2. Отдельно проверить на бэкенде: примет ли API некорректный телефон, если отправить запрос напрямую (клиентская валидация не защищает данные сама по себе).
3. Уточнить у команды точный требуемый формат (только `+998`? допускается ли ввод без `+998`, локальные номера?) — это влияет на regex. При необходимости оформить как вопрос в `03-questions-for-team.md`.

**Приоритет:** P2 (нарушение контроля доступа, но окно ограничено ~15 мин)   **Статус:** 🔴 Новый   **Дата:** 23.07.2026

**Описание:**
Деактивация не действует немедленно. Новый вход деактивированного РОП корректно запрещается. Но если РОП **уже открыл сессию** до деактивации, он продолжает пользоваться системой как ни в чём не бывало — открываются страницы, проходят запросы. 1. Проверка авторизации на каждом запросе (`RequireAuth`) проверяет только подпись и срок действия токена, но **не сверяет `IsActive`** пользователя.

3. Вернуться во вкладку РОП и продолжить работать: открывать страницы, выполнять действия.

**Ожидаемый результат:**
После деактивации доступ прекращается **сразу** (или в течение секунд): следующий же запрос отклоняется, пользователя разлогинивает. Деактивация «уволенного» должна действовать немедленно.

**Фактический результат:**
Деактивированный РОП продолжает полноценно работать до истечения текущего access-токена — до ~15 минут. Всё это время его запросы проходят.
