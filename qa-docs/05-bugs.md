На production могли остаться тестовые РОП и изменённые тарифы — **нужно найти и удалить тестовые данные или вернуть прежние значения**, чтобы они не мешали реальной работе. Список созданных и изменённых данных нужно зафиксировать.
> 2. **Впредь функциональные проверки (создание, редактирование, деактивация) выполняем на staging/test, а не на проде** — по правилу проекта. На проде допустимо только пассивное наблюдение (открыть страницу, посмотреть), без изменения данных.
>
> **[обновлено 25.07] ✅ Доступ к окружениям получен** — и к staging, и к production. Проблема «проверять негде» снята.
>
> **Правило с этого момента:**
>
> | Окружение | Что делаем |
> | --- | --- |
> | **staging** | Все функциональные проверки: создание, изменение, удаление, воспроизведение дефектов, автотесты |
> | **production** | **Только пассивное наблюдение.** Открыть страницу, посмотреть. Ничего не менять |
>
> Доступ к проду — это возможность разобрать инцидент и сверить поведение, **а не разрешение там тестировать**.
>
> **Два следствия для этого файла:**
>
> 1. **У всех восьми дефектов в поле «Окружение» стоит production.** Их нужно **перепроверить на staging** — часть могла быть уже починена вместе с другими работами. До перепроверки статусы остаются «Новый»;
> 2. **Долг по проду:** тестовые руководители отделов, изменённые тарифы и деактивированный пользователь, оставшиеся после июльских проверок, нужно найти и убрать. Список — в предупреждении выше.

### BUG-001. Кнопка показа пароля отображается текстом вместо иконки

<a id="bug-002"></a>
### BUG-002. 🔒 Экран входа предзаполнен данными супер-администратора

Web | Admin — экран входа (до авторизации) | production | При открытии страницы входа поля «Логин» и «Пароль» уже заполнены рабочими данными супер-администратора. Пользователю достаточно нажать «Войти».

**Приоритет:** P1 — проблема безопасности   **Статус:** 🟢 Исправлен (по сообщению команды 31.07.2026; повторная проверка не выполнялась)   **Дата:** 23.07.2026

**Описание:**
Форма входа открывается с уже заполненными логином и паролем супер-администратора. Это рабочие данные, а не пример или подсказка. Любой человек, который открыл страницу, может попытаться войти с максимальными правами, не зная логина и пароля. На production это критическая проблема безопасности.

**Шаги:**
1. Открыть страницу входа в Admin.
2. Не вводя ничего, посмотреть на поля «Логин» и «Пароль» — они уже заполнены.
3. На staging нажать «Войти».

> ⚠️ На production третий шаг выполнять только с разрешения ответственного сотрудника.

**Ожидаемый результат:**
Поля «Логин» и «Пароль» пустые. Данные супер-администратора не отображаются на странице и не доступны посетителю.

**Фактический результат:**
Поля заполнены рабочими данными сразу после открытия страницы. Вход с правами супер-администратора возможен без самостоятельного ввода логина и пароля. Проблема обнаружена на production.

**Вложение:**
`Снимок экрана — 2026-07-23 в 13.44.10.png`

**Дополнительная проверка:**
1. Убедиться, что поля пустые после обычного открытия страницы и после обновления страницы.
2. Проверить staging и production без выполнения входа на production.
3. Убедиться, что старые общие данные больше не дают доступ.
4. Проверить историю входов на наличие подозрительной активности.

### BUG-006. 🔒 Деактивация пользователя не завершает уже открытую frontend-сессию

Web (Safari) / API | Admin — вход и деактивация пользователя | production (23.07.2026), подтверждён на staging (29.07.2026) | Backend блокирует запросы деактивированной сессии, но frontend не закрывает её; после повторной активации старая вкладка снова работает без входа.

**Описание:**
При исходной проверке на production деактивированный РОП продолжал работать в уже открытой сессии примерно до 15 минут. На staging поведение backend улучшено: защищённые запросы с access token деактивированного оператора сразу и через 35 секунд возвращают HTTP 401 с сообщением `Hisob faol emas`.

Однако frontend в Safari не завершает локальную сессию и не перенаправляет пользователя на страницу входа. Вкладка «Звонки» остаётся открытой. После повторной активации оператора эта же старая вкладка снова работает без повторного ввода логина и пароля. Значит, деактивация временно блокирует запросы, но не отзывает существующую сессию окончательно.

**Связанный кейс:** TC-013

**Шаги:**
1. На staging войти в Safari под тестовым оператором и открыть раздел «Звонки».
2. В другой сессии войти под РОП этого оператора.
3. Деактивировать оператора через `PATCH /v1/users/{id}` с `is_active=false`.
4. В течение 45 секунд наблюдать открытую вкладку оператора и выполнить защищённый запрос сразу и через 35 секунд.
5. Активировать оператора обратно через `PATCH /v1/users/{id}` с `is_active=true`.
6. Не выполняя повторный вход в Safari, проверить старую вкладку оператора.

**Ожидаемый результат:**
При следующем защищённом запросе или heartbeat frontend очищает локальную сессию и открывает страницу входа. Access token и refresh-сессия отзываются; последующая активация пользователя не восстанавливает старую вкладку — требуется новый вход.

**Фактический результат:**
1. Исходный вход оператора и доступ к истории звонков вернули HTTP 200.
2. После деактивации защищённый запрос со старым access token сразу и через 35 секунд вернул HTTP 401, `detail="Hisob faol emas"`.
3. Safari не открыл страницу входа: вкладка оператора осталась открытой.
4. После обратной активации старая вкладка продолжила работать без повторного входа.
5. Повторяемость актуальной staging-проверки: 1 из 1.

**Вложение:**
Диагностический вывод API-проверки TC-013 от 29.07.2026 и ручное наблюдение открытой вкладки Safari. Тестовый оператор после проверки активирован обратно; контрольный вход вернул HTTP 200.

**Дополнительная проверка:**
1. Обрабатывать ответ деактивации во frontend: очистить access token, данные пользователя и открыть страницу входа.
2. Проверить одинаковое завершение сессии для ответов HTTP 401 и 403.
3. Отзывать действующие access/refresh-сессии при деактивации, чтобы повторная активация не оживляла старую вкладку.
4. Повторить сценарий отдельно для Оператора и РОП в Safari, Chrome и Firefox.
5. Проверить, что после деактивации нельзя открыть новые разделы, изменить данные или продолжить просмотр ранее загруженных закрытых данных.

3. Передать `Access-Control-Request-Method: GET`.
4. Передать `Access-Control-Request-Headers: authorization`.
5. Проверить HTTP-код и все заголовки `Access-Control-Allow-*`.
6. Автотестом повторить безопасный `GET /v1/auth/me` с тестовым bearer token и

**Ожидаемый результат:**
Неизвестный origin отсутствует в allowlist и не получает

других официальных клиентов API.

**Фактический результат:**
Ручной preflight вернул HTTP 204 и заголовки:

```text
Access-Control-Allow-Origin: https://untrusted.invalid
Access-Control-Allow-Credentials: true
Access-Control-Allow-Headers: Content-Type,Authorization,X-Request-Id
Access-Control-Allow-Methods: GET,POST,PUT,PATCH,DELETE,OPTIONS
```

Автотест подтвердил, что защищённый `GET /v1/auth/me` с тестовым bearer token

**Вложение:**

2. Автотест

**Дополнительная проверка:**
