> **Два предупреждения по процессу:**
> 1. **Мы создавали и меняли данные на боевой системе.** Часть багов проверялась действиями, которые изменяют production: создание РОП (BUG-007), редактирование тарифа (BUG-008), деактивация РОП (BUG-006). На production могли остаться тестовые РОП и изменённые тарифы — **нужно найти и удалить тестовые данные или вернуть прежние значения**, чтобы они не мешали реальной работе. Список созданных и изменённых данных нужно зафиксировать.
> 2. **Впредь функциональные проверки (создание, редактирование, деактивация) выполняем на staging/test, а не на проде** — по правилу проекта. На проде допустимо только пассивное наблюдение (открыть страницу, посмотреть), без изменения данных.
>
> **[обновлено 25.07] ✅ Доступ к окружениям получен** — и к staging, и к production. Проблема «проверять негде» снята.
>
> **Правило с этого момента:**
>
> | Окружение | Что делаем |
> | --- | --- |
> | **staging** | Все функциональные проверки: создание, изменение, удаление, воспроизведение дефектов, автотесты |
> | **production** | **Только пассивное наблюдение.** Открыть страницу, посмотреть. Ничего не менять |
>
> Доступ к проду — это возможность разобрать инцидент и сверить поведение, **а не разрешение там тестировать**.

> **Два следствия для этого файла:**

> 1. **У всех восьми дефектов в поле «Окружение» стоит production.** Их нужно **перепроверить на staging** — часть могла быть уже починена вместе с другими работами. До перепроверки статусы остаются «Новый»;
> 2. **Долг по проду:** тестовые руководители отделов, изменённые тарифы и деактивированный пользователь, оставшиеся после июльских проверок, нужно найти и убрать. Список — в предупреждении выше.

### BUG-001. Кнопка показа пароля отображается текстом вместо иконки

Web | Admin — экран входа (до авторизации) | production | В поле «Пароль» кнопка показа пароля отображается словом «показать» вместо иконки глаза.

**Приоритет:** P3 (косметический, на функциональность не влияет)   **Статус:** 🔴 Новый   **Дата:** 23.07.2026

**Описание:**
На странице входа справа в поле «Пароль» есть кнопка, которая показывает или скрывает введённый пароль. Сейчас кнопка отображается текстом «показать». По дизайну на её месте должна быть иконка глаза.

**Шаги:**
1. Открыть страницу входа в Admin.
2. Посмотреть на правую часть поля «Пароль».

**Ожидаемый результат:**
В правой части поля отображается иконка глаза. При нажатии пароль показывается или скрывается, а состояние иконки меняется.

**Фактический результат:**
Вместо иконки отображается текст «показать».

**Вложение:**
`Снимок экрана — 2026-07-23 в 13.40.53.png`

**Дополнительная проверка:**
1. Проверить кнопку до и после ввода пароля.
2. Проверить русскую и узбекскую версии интерфейса.
3. Предзаполненные данные входа на том же экране относятся к отдельному BUG-002.

<a id="bug-002"></a>
### BUG-002. 🔒 Экран входа предзаполнен данными супер-администратора

Web | Admin — экран входа (до авторизации) | production | При открытии страницы входа поля «Логин» и «Пароль» уже заполнены рабочими данными супер-администратора. Пользователю достаточно нажать «Войти».

**Приоритет:** P1 — проблема безопасности   **Статус:** 🔴 Новый   **Дата:** 23.07.2026

**Описание:**
Форма входа открывается с уже заполненными логином и паролем супер-администратора. Это рабочие данные, а не пример или подсказка. Любой человек, который открыл страницу, может попытаться войти с максимальными правами, не зная логина и пароля. На production это критическая проблема безопасности.

**Шаги:**
1. Открыть страницу входа в Admin.
2. Не вводя ничего, посмотреть на поля «Логин» и «Пароль» — они уже заполнены.
3. На staging нажать «Войти».

> ⚠️ На production третий шаг выполнять только с разрешения ответственного сотрудника.

**Ожидаемый результат:**
Поля «Логин» и «Пароль» пустые. Данные супер-администратора не отображаются на странице и не доступны посетителю.

**Фактический результат:**
Поля заполнены рабочими данными сразу после открытия страницы. Вход с правами супер-администратора возможен без самостоятельного ввода логина и пароля. Проблема обнаружена на production.

**Вложение:**
`Снимок экрана — 2026-07-23 в 13.44.10.png`

**Дополнительная проверка:**
1. Убедиться, что поля пустые после обычного открытия страницы и после обновления страницы.
2. Проверить staging и production без выполнения входа на production.
3. Убедиться, что старые общие данные больше не дают доступ.
4. Проверить историю входов на наличие подозрительной активности.

### BUG-004. Поле «Телефон» принимает буквы и любой текст (нет проверки формата)

Web | Admin — Супер-администратор, форма «Создать РОП» | production | Поле «Телефон» принимает буквы и посторонние символы. Формат номера не проверяется.

**Приоритет:** P2 (пропускает некорректные данные в систему)   **Статус:** 🔴 Новый   **Дата:** 23.07.2026

**Описание:**
В форме создания РОП поле «Телефон» не проверяет введённое значение. Пользователь может указать буквы или произвольные символы и отправить форму. Из-за этого в системе могут сохраняться некорректные номера телефонов.

**Шаги:**
1. Войти как Супер-администратор и открыть раздел «РОП».
2. Нажать «Создать РОП».
3. В поле «Телефон» ввести буквы или произвольный текст.
4. Заполнить остальные обязательные поля корректно и нажать «Создать».

**Ожидаемый результат:**
Поле принимает только номер телефона в утверждённом формате. При вводе букв или неподходящего количества цифр форма показывает понятную ошибку и не создаёт РОП.

**Фактический результат:**
Поле принимает любой непустой текст, включая буквы. Сообщение об ошибке не появляется.

**Вложение:**
`Снимок экрана — 2026-07-23 в 13.48.33.png`

**Дополнительная проверка:**
1. Проверить поле «Телефон» при создании и редактировании РОП.
2. Проверить создание и редактирование оператора.
3. Проверить пустое значение, слишком короткий и слишком длинный номер, буквы и специальные символы.
4. Уточнить у команды допустимый формат: только номера с +998 или также другие варианты.

Web | Admin / Интерфейс оператора — редактирование учётной записи | staging | Если РОП меняет данные уже вошедшего оператора, оператор продолжает работать в открытом сеансе.

**Приоритет:** P2 (активный сеанс продолжает работать с устаревшими данными)   **Статус:** 🔴 Новый   **Дата:** 27.07.2026

**Описание:**
Оператор входит в систему, после чего РОП изменяет и сохраняет его данные. Открытый сеанс оператора не завершается. Оператор продолжает работать без повторного входа, хотя данные его учётной записи уже изменились.

**Шаги:**
1. Войти в систему как Оператор и оставить страницу открытой.
2. В другом браузере или окне войти как РОП.
3. Открыть данные этого оператора, изменить их и сохранить.
4. Вернуться в открытый сеанс оператора и продолжить работу.

**Ожидаемый результат:**
После сохранения изменений активный сеанс оператора завершается. Оператор должен повторно войти с актуальными данными.

**Фактический результат:**
Оператор остаётся в системе и продолжает работать без повторного входа.

**Вложение:**
Нет.

**Дополнительная проверка:**
1. Отдельно проверить изменение логина, пароля, имени, телефона и настроек телефонии.
2. Проверить, завершается ли сеанс сразу или только после обновления страницы.
3. Проверить тот же сценарий для РОП.
4. Сравнить поведение с деактивацией пользователя из BUG-006.

### BUG-017. Во время звонка поле «Оператор» позволяет выбрать другого оператора

Web | Интерфейс оператора — форма активного звонка | staging | Поле «Оператор» отображается выпадающим списком, хотя должно автоматически содержать текущего оператора.

**Приоритет:** P2 (звонок может быть записан на другого сотрудника)   **Статус:** 🔴 Новый   **Дата:** 27.07.2026

**Описание:**
Во время звонка оператор заполняет поля по клиенту. Поле «Оператор» позволяет выбрать сотрудника из списка. Пользователь может случайно или намеренно указать другого человека, из-за чего история звонка и статистика будут связаны не с тем оператором.

**Шаги:**
1. Войти как Оператор.
2. Начать звонок клиенту из очереди.
3. Открыть поле «Оператор» в форме звонка.
4. Посмотреть доступные значения и попробовать выбрать другого сотрудника.

**Ожидаемый результат:**
Поле автоматически заполнено именем вошедшего оператора и недоступно для изменения.

**Фактический результат:**
Поле отображается выпадающим списком и позволяет выбрать другого оператора.

**Вложение:**
Нет.

**Дополнительная проверка:**
1. Убедиться, что в сохранённом результате звонка указан вошедший оператор.
2. Проверить повторный звонок и звонок после обновления страницы.
3. Проверить отображение оператора в отчётах и истории клиента.

### BUG-018. Рабочее расписание не ограничивает очередь и звонки оператора

Web | Интерфейс оператора — рабочий день и очередь звонков | staging | После окончания рабочего дня очередь остаётся доступной, и оператор всё ещё может звонить клиентам.

**Приоритет:** P2 (ограничения рабочего времени не применяются)   **Статус:** 🔴 Новый   **Дата:** 27.07.2026

**Описание:**
Настройки начала и окончания рабочего дня не ограничивают работу оператора. После указанного времени окончания очередь продолжает отображаться, а кнопка звонка остаётся доступной. Оператор может звонить клиентам вне установленного рабочего времени.

**Шаги:**
1. Войти как РОП и установить оператору время начала и окончания рабочего дня.
2. Войти как Оператор до окончания рабочего дня.
3. Дождаться времени окончания или установить его на ближайшее время.
4. После окончания рабочего дня проверить очередь и попытаться начать звонок.

**Ожидаемый результат:**
До начала и после окончания рабочего дня очередь недоступна, а начать звонок нельзя. Оператор видит понятное сообщение о том, что рабочий день ещё не начался или уже завершён.

**Фактический результат:**
После окончания рабочего дня очередь остаётся на экране, и оператор может начать звонок клиенту.

**Вложение:**
Нет.

**Дополнительная проверка:**
1. Проверить поведение до начала рабочего дня.
2. Проверить точное время начала и окончания, включая переход на следующую минуту.
3. Проверить часовой пояс пользователя и сервера.
4. Проверить обновление страницы и повторный вход после окончания рабочего дня.
5. Убедиться, что ограничение действует и на автоматический, и на ручной запуск звонка.

### BUG-019. После входа оператор попадает на «Рабочий стол» вместо раздела «Звонки»

Web | Admin — Оператор, вход | staging | После успешной авторизации оператор перенаправляется на `/dashboard/home` вместо стартового раздела `/dashboard/calls`.

**Приоритет:** P2   **Статус:** ⚪ Не баг   **Дата:** 28.07.2026

**Результат триажа от 28.07.2026:**
Поведение `/dashboard/home` подтверждено владельцем продукта как корректное. Причина расхождения — устаревший ожидаемый результат TC-003, а не дефект приложения. TC-003 и его автотест синхронно обновлены с пометкой «уточнено по факту, 28.07.2026»; `xfail` удалён.

**Описание:**
При первичной проверке TC-003 и локальная логика фронтенда указывали раздел «Звонки» как стартовую страницу оператора. На staging учётные данные принимались, авторизация завершалась успешно, но открывался «Рабочий стол». После уточнения требования это поведение признано корректным.

**Шаги:**
1. Открыть страницу входа Admin на staging без активной сессии.
2. Ввести корректные логин и пароль оператора.
3. Нажать «Войти».
4. Проверить адрес и содержимое открывшейся страницы.

**Первоначальный ожидаемый результат:**
Открывается `/dashboard/calls`: видна таблица лидов раздела «Звонки» и доступно меню оператора.

**Фактический результат:**
Открывается `/dashboard/home`: отображается «Рабочий стол» оператора. Авторизация успешна, пункты меню оператора доступны.

**Уточнённый корректный результат от 28.07.2026:**
После успешного входа оператор попадает на `/dashboard/home`. На странице видны блок «Последние звонки», кнопка «Начать звонок» и меню оператора.

**Вложение:**
Playwright сохранил screenshot и trace локально в `test-results` при падении TC-003. Артефакты не добавлены в Git, потому что могут содержать тестовые данные.

**Дополнительная проверка:**
1. Синхронизировать `getDefaultDashboardPath` с подтверждённым стартовым адресом `/dashboard/home`.
2. Проверить стартовые страницы РОП и супер-администратора.

### BUG-020. Форма входа и API используют разную минимальную длину пароля

Web | Admin — экран входа | staging | Форма разрешает отправить пароль из 6 или 7 символов, но API входа требует минимум 8 и возвращает техническое сообщение `validation failed`.

**Приоритет:** P2 (рассинхрон контракта авторизации)   **Статус:** 🔴 Новый   **Дата:** 28.07.2026

**Описание:**
По TC-007 минимальная длина пароля на входе — 6 символов: 5 символов должны блокироваться клиентской валидацией, а 6 — отправляться как обычная попытка входа. Форма именно так и работает. Однако контракт `POST /v1/auth/login` в текущем backend-коде содержит `minLength:"8"`. Поэтому пароль из 6 символов отклоняется до проверки учётных данных, а пользователь видит английское техническое сообщение вместо универсальной ошибки входа.

**Шаги:**
1. Открыть страницу входа Admin на staging без активной сессии.
2. Ввести любой несуществующий логин.
3. Ввести пароль `12345` и нажать «Войти».
4. Убедиться, что запрос не отправлен и показано сообщение «Пароль должен содержать не менее 6 символов!».
5. Исправить пароль на `123456` и снова нажать «Войти».
6. Проверить показанное сообщение.

**Ожидаемый результат:**
Для 6 символов клиентская подсказка исчезает, отправляется один запрос входа, после чего для неверных данных показывается универсальное сообщение `login yoki parol noto'g'ri`.

**Фактический результат:**
Запрос отправляется, но API отклоняет пароль своей границей минимум 8 символов. В красной плашке отображается `validation failed`.

**Вложение:**
Диагностичный вывод pytest для TC-007; screenshot и trace создаются Playwright только при падении.

**Дополнительная проверка:**
1. Согласовать единую минимальную длину пароля для формы входа и API.
2. Проверить границы 5, 6, 7 и 8 символов на UI и API.
3. Убедиться, что существующие пользователи с паролем из 6–7 символов могут войти либо получают локализованную инструкцию.
4. После исправления повторить TC-007 и удалить `xfail` только после XPASS с `strict=True`.
