# Ежедневный happy-path UAT: запуск и сопровождение

**Дата:** 03.08.2026
**Статус:** техническая обвязка, Telegram-доставка и GitHub Actions включены;
ежедневный запуск настроен на 08:00 `Asia/Tashkent`; часть внешних ресурсов ещё
требует настройки

## Что реализовано

- Маркер `daily_uat` выбирает только 33 утверждённых UAT-ID.
- Один pytest-item соответствует одному UAT-ID.
- Каждый запуск пишет JUnit, screenshot/trace, текстовый и JSON-отчёт в новый
  каталог `uat-results/<timestamp>`.
- Генератор объединяет результат с полным чеклистом и всегда показывает три
  числа: проверяемо, заблокировано дефектом и всего.
- Telegram получает только человеческий отчёт без traceback и секретов.

## Локальный запуск

Из корня проекта:

```bash
.venv/bin/python scripts/run_daily_uat.py --telegram auto
```

Режимы доставки:

- `auto` — отправить, только если заданы обе обязательные Telegram-переменные;
- `always` — считать отсутствие/ошибку доставки ошибкой прогона;
- `never` — сформировать только локальный отчёт;
- `dry-run` — показать точный текст сообщения без отправки.

Для повторяемой диагностики можно передать дополнительный аргумент pytest:

```bash
.venv/bin/python scripts/run_daily_uat.py \
  --telegram never \
  --pytest-arg=-k \
  --pytest-arg=UAT-SYS-001
```

## Telegram

В локальном `.env` или защищённых CI variables должны находиться:

```dotenv
TELEGRAM_BOT_TOKEN=<секрет BotFather>
TELEGRAM_CHAT_ID=<ID личного или группового чата>
TELEGRAM_THREAD_ID=<необязательно, ID topic>
```

Токен и chat ID запрещено добавлять в git, документацию, логи и сообщения
задач. После добавления значений доставка проверяется командой:

```bash
.venv/bin/python scripts/send_uat_report.py uat-results/<run>/report.txt
```

## Расписание

За расписание отвечает `.github/workflows/daily-uat.yml`. GitHub Actions
ежедневно в **08:00 `Asia/Tashkent`** запускает Ubuntu runner, устанавливает
Python-зависимости и Chromium, после чего выполняет:

```bash
python scripts/run_daily_uat.py --telegram always --capture-pytest-output
```

Workflow также можно запустить вручную через вкладку **Actions → Daily
happy-path UAT → Run workflow**. Параллельные прогоны одной staging-среды
запрещены через `concurrency`.

GitHub runner получает staging-реквизиты и Telegram-настройки только из
Repository Secrets. Сырой pytest-лог, screenshot и trace остаются на временном
runner и не публикуются, поскольку репозиторий публичный. В Actions на 14 дней
сохраняются только `report.txt` и `summary.json`.

Расписание GitHub срабатывает по последнему commit default-ветки. Плановый
запуск может начаться с небольшой задержкой из-за очереди GitHub; это не меняет
время, указанное в самом отчёте.

Параллельный регресс не может затереть UAT: каталог каждого UAT-прогона
уникален. Ранее подготовленный локальный LaunchAgent отключён из-за ограничения
macOS на фоновый доступ к проекту в `Documents`.

Первый стабильный серверный прогон выполнен 03.08.2026: pytest завершился без
тестовых падений, 12 из 27 проверяемых сценариев прошли, 15 остались «не
выполнено» из-за внешних ворот, ещё 6 заблокированы подтверждёнными дефектами.
Telegram-доставка отчёта подтверждена. Подробности находятся в
[`16-daily-uat-github-run-2026-08-03.md`](16-daily-uat-github-run-2026-08-03.md).

## Внешние ворота

Для полного зелёного набора нужны:

- URL staging Landing и удаляемый demo-канал;
- отдельные тестовые AmoCRM и OnlinePBX;
- безопасный телефон, extension и Gemini quota;
- детерминированные тестовые лиды для очереди и статусных переходов;
- разрешение временно изменять тариф, воронки, подсказки и критерии с
  обязательным восстановлением;
- исправления BUG-014, 017, 024, 026, 027, 029, 038 и 045.

Отсутствующий ресурс не превращается в `pass`: сценарий остаётся среди
проверяемых и показывается как «не выполнено».

## Дисциплина красного дня

Красный результат разбирается в тот же день:

1. Дефект продукта — зарегистрировать баг; сценарий временно перевести в
   `blocked_defect` только после подтверждения причины.
2. Намеренное изменение поведения — одновременно обновить UAT-тест и описание
   кейса; раздельное изменение запрещено.
3. Слабость теста — исправить ожидание, данные или cleanup, не удаляя проверку.

Категории «просто флак» нет. Причину нужно воспроизвести. Проверки не ослабляются
ради зелёного; фиксированные задержки не добавляются, используются ожидания
условия с таймаутом. Перед запуском браузерные процессы должны быть чистыми.
