BUG-006. Foydalanuvchi deaktivatsiya qilingandan keyin ochiq frontend sessiyasi tugamaydi
-------------------------------------------------------------------------------------------

Web (Safari) / API | Admin — kirish va foydalanuvchini deaktivatsiya qilish | production (23.07.2026), stagingda tasdiqlandi (29.07.2026) | Backend deaktivatsiya qilingan sessiya so'rovlarini bloklaydi, ammo frontend sessiyani yopmaydi; qayta aktivatsiyadan keyin eski sahifa yangi kirishsiz yana ishlaydi.

Muhimlik: P2, sessiya butunlay tugamaydi va foydalanuvchi kirish sahifasiga qaytarilmaydi
Holat: Tuzatilgan (31.07.2026 jamoa xabariga ko'ra; tuzatish qayta tekshirilmagan)
Sana: 23.07.2026
Qayta tekshiruv: 29.07.2026

Tavsif:
Productiondagi dastlabki tekshiruvda deaktivatsiya qilingan ROP oldindan ochilgan sessiyada taxminan 15 daqiqagacha ishlashda davom etgan. Stagingda backend xatti-harakati yaxshilangan: deaktivatsiya qilingan operatorning access tokeni bilan yuborilgan himoyalangan so'rovlar darhol va 35 soniyadan keyin HTTP 401 hamda `Hisob faol emas` xabarini qaytaradi.

Ammo Safari frontend lokal sessiyani tugatmaydi va foydalanuvchini kirish sahifasiga yo'naltirmaydi. «Qo'ng'iroqlar» sahifasi ochiq qoladi. Operator qayta aktivatsiya qilingandan keyin ayni eski sahifa login va parolni qayta kiritmasdan yana ishlaydi. Demak, deaktivatsiya so'rovlarni vaqtincha bloklaydi, ammo mavjud sessiyani butunlay bekor qilmaydi.

Bog'liq test: TC-013

Qadamlar:
1. Stagingda Safari orqali test operatori sifatida kiring va «Qo'ng'iroqlar» bo'limini oching.
2. Boshqa sessiyada shu operatorning ROP hisobiga kiring.
3. `PATCH /v1/users/{id}` so'rovida `is_active=false` yuborib operatorni deaktivatsiya qiling.
4. 45 soniya davomida operatorning ochiq sahifasini kuzating va himoyalangan so'rovni darhol hamda 35 soniyadan keyin yuboring.
5. `PATCH /v1/users/{id}` so'rovida `is_active=true` yuborib operatorni qayta aktivatsiya qiling.
6. Safarida qayta kirmasdan operatorning eski sahifasini tekshiring.

Kutilgan natija:
Keyingi himoyalangan so'rov yoki heartbeat paytida frontend lokal sessiyani tozalaydi va kirish sahifasini ochadi. Access token va refresh sessiyasi bekor qilinadi; foydalanuvchini keyin qayta aktivatsiya qilish eski sahifani tiklamaydi va yangi kirish talab qilinadi.

Haqiqiy natija:
1. Operatorning dastlabki kirishi va qo'ng'iroqlar tarixiga kirish HTTP 200 qaytardi.
2. Deaktivatsiyadan keyin eski access token bilan himoyalangan so'rov darhol va 35 soniyadan keyin HTTP 401, `detail="Hisob faol emas"` qaytardi.
3. Safari kirish sahifasini ochmadi: operator sahifasi ochiq qoldi.
4. Qayta aktivatsiyadan keyin eski sahifa yangi kirishsiz ishlashda davom etdi.
5. Stagingdagi dolzarb tekshiruv takrorlanishi: 1 ta urinishdan 1 tasi.

Ilova:
29.07.2026 kungi TC-013 API diagnostik chiqishi va Safari ochiq sahifasining qo'lda kuzatuvi. Tekshiruvdan keyin test operatori qayta aktivatsiya qilindi; nazorat kirishi HTTP 200 qaytardi.

Qo'shimcha tekshiruv:
1. Frontend deaktivatsiya javobini qayta ishlashi kerak: access token va foydalanuvchi ma'lumotlarini tozalab, kirish sahifasini oching.
2. HTTP 401 va 403 javoblarida sessiya bir xil tugashini tekshiring.
3. Qayta aktivatsiya eski sahifani qayta jonlantirmasligi uchun deaktivatsiya paytida amaldagi access/refresh sessiyalarini bekor qiling.
4. Ssenariyni Operator va ROP uchun Safari, Chrome va Firefox brauzerlarida alohida takrorlang.
5. Deaktivatsiyadan keyin yangi bo'limlarni ochish, ma'lumotlarni o'zgartirish yoki oldindan yuklangan yopiq ma'lumotlarni ko'rishni davom ettirish mumkin emasligini tekshiring.
