# Автотесты Operator AI

Автотесты запускаются только на `staging` или `test`. Production блокируется
проверкой `OPERATOR_AI_TARGET_ENV`, а URL по умолчанию отсутствуют.

## Текущее покрытие

Автоматически выполняются проверки:

- TC-001–TC-010 — вход, ошибки авторизации и выход;
- TC-012 — деактивация блокирует новый вход и уже выданный access token,
  данные оператора сохраняются, повторная активация возвращает доступ;
- TC-014–TC-015 — самостоятельная смена пароля и неверный старый пароль;
- TC-016–TC-017 — несовпадающий повтор и граница нового пароля 7/8 символов;
- TC-018 — РОП сбрасывает пароль своему оператору;
- TC-020 — двойной клик по кнопке входа отправляет один запрос;
- TC-021–TC-033 и TC-040–TC-042 — меню ролей, прямые URL, RBAC и
  изоляция компаний;
- TC-034–TC-038 — межклиентская изоляция реальных AmoCRM-лидов, воронок,
  статусов, звонков, transcript-endpoint и посещаемости. Текущий РОП
  используется только для чтения как компания Б, компания А создаётся
  временно и полностью удаляется после прогона;
- TC-039 — после logout РОП browser Back на предыдущий защищённый маршрут и
  reload оставляют страницу входа; токен и пользователь удалены из storage,
  таблица кабинета не появляется даже кратковременно;
- TC-043 — после logout вход Оператором в том же браузере полностью заменяет
  роль РОП в API-ответе, browser storage и меню; прямой URL «Критериев» не
  показывает данные и не вызывает защищённый API;
- TC-044 — супер-админ создаёт активного РОП, проверяет строку, API и вход,
  затем удаляет тестового пользователя; отсутствие обязательных
  Super-admin credentials является явной ошибкой конфигурации;
- TC-047–TC-048 — повторный телефон в другом форматировании и повторный
  логин отклоняются понятной ошибкой; второй РОП не создаётся, исходная
  временная запись удаляется после проверки;
- TC-049 — супер-админ редактирует отдельного тестового РОП; новые имя,
  фамилия, телефон и компания сохраняются после reload, а ID, `company_id`,
  логин и роль остаются прежними без появления дубликата;
- TC-050 — UI-деактивация тестового РОП сразу блокирует старый токен и новый
  вход, не меняет данные; после UI-активации вход и компания восстанавливаются;
- TC-051 — удаление отдельного тестового РОП требует подтверждения: отмена
  сохраняет запись, подтверждение удаляет её из UI и API, повторный вход
  возвращает 401;
- TC-052 — создание оператора со свободным внутренним номером и проверка входа;
- TC-053 — пустая форма оператора остаётся заблокированной и не отправляет
  `POST`; после обычного focus/blur подсказки обязательны для имени, фамилии,
  пароля, имени пользователя и зарплаты (контракт уточнён по факту 30.07.2026);
- TC-054 — занятый внутренний номер недоступен для выбора
  (`xfail`, подтверждённый BUG-023);
- TC-055 — при недоступном списке OnlinePBX появляется резервное поле
  extension; пустое значение показывает обязательность, блокирует кнопку и
  не отправляет запрос создания оператора;
- TC-056 — знак минус в зарплате фильтруется (`-1` превращается в `1`),
  ноль отклоняется, положительное значение принимается; оператор не создаётся
  (контракт уточнён по факту 30.07.2026);
- TC-057–TC-059 — уникальность телефона и логина, редактирование оператора;
- TC-060 — карточка показывает назначенную оператору воронку
  (`xfail`, подтверждённый BUG-024);
- TC-060 — переход из карточки открывает данные выбранного звонка без
  `deal_id` (`xfail`, подтверждённый BUG-027);
- TC-062 — форма создания РОП принимает 300-символьные имя, логин и название
  компании без зависания, HTTP 500, обрезания или дублирования; сохранённые
  значения повторно сверяются через API, временный РОП удаляется;
- TC-063 — двойное нажатие «Создать» не дублирует оператора;
- TC-064 — первый запрос создания РОП принудительно обрывается: интерфейс
  показывает сетевую ошибку, сохраняет заполненную форму и не создаёт
  «призрак»; повтор после восстановления создаёт ровно одну запись;
- TC-065 — операторский список рабочих лидов сверяет название, статус,
  попытки и последний звонок с API; выбранная строка открывает карточку той же
  сделки, а «Назад» возвращает к списку;
- TC-167 — пустая и поочерёдно неполная форма подключения AmoCRM показывает
  обязательность всех шести реквизитов, не отправляет POST и оставляет
  временного РОП без подключения;
- TC-201 — пустые Domain и API key OnlinePBX показывают обязательность,
  блокируют POST; после reload и повторного открытия конфигурация отсутствует;
- TC-208 — роли РОП и Оператор получают HTTP 403 на чтение, создание,
  изменение и удаление конфигураций OnlinePBX; безопасный снимок списка до и
  после запрещённых запросов остаётся неизменным;
- TC-209 — сохранённый OnlinePBX API key не должен возвращаться в list/detail
  API (`xfail`, подтверждённый BUG-032: backend возвращает восстанавливаемый
  `call_token` открытым текстом; значение секрета тест не выводит);
- TC-227 — Super-admin видит ровно три фиксированных тарифа; карточки, порядок,
  цены, состояния, описания и возможности сверяются с публичным API;
- TC-228 — публичный список тарифов.
- TC-232 — пустое или состоящее из пробелов название тарифа показывает
  обязательность, блокирует кнопку и не отправляет `PATCH`; исходный тариф
  остаётся без изменений в UI и API;
- TC-233 — при пользовательском вводе знак минуса не удерживается в поле
  цены; отрицательный `price` через прямой API отклоняется, исходный тариф
  остаётся без изменений;
- TC-241 — РОП и Оператор получают HTTP 403 при попытке обновить тариф,
  запрос без токена — HTTP 401; публичный список до и после совпадает;
- TC-242 — PATCH с кодами `premium`, `FULL_AI` и пробелом отклоняется;
  четвёртый тариф не создаётся, набор трёх допустимых кодов не меняется;
- TC-243 — во всех трёх редакторах тарифа отсутствуют поле системного кода,
  создание и удаление; read-only проход не меняет публичный API;
- TC-253 — чистые браузерные контексты выбирают русский или узбекский по
  locale, а неподдерживаемый английский безопасно использует узбекский fallback;
- TC-254 — язык формы входа переключается RU/UZ без reload и потери уже
  введённых логина и пароля; меню содержит ровно два языка и сохраняет выбор;
- TC-255 — открытый кабинет РОП синхронно переключает меню, заголовок,
  таблицу и форму создания оператора RU/UZ без reload и изменяющих запросов;
- TC-256 — выбранный русский язык сохраняется после reload, перехода,
  logout, новой вкладки и повторного входа той же ролью;
- TC-257 — неподдерживаемое, пустое и 5000-символьное значение языка не ломает
  форму и не показывает сырые ключи; выбор русского восстанавливает storage;
- TC-258 — полный набор меню Super-admin, РОП и Оператора сверяется на RU/UZ;
  встроенный поиск находит разрешённый раздел по текущему языку;
- TC-259 — клиентские подсказки и отказ неверного входа проверяются на RU/UZ:
  узбекский вариант проходит, русский помечен `xfail` по подтверждённому
  BUG-033 — backend-текст остаётся узбекским;
- TC-261 — окно смены пароля и mismatch-валидация проверяются на RU/UZ без
  отправки POST; русский вариант `xfail` по BUG-034, потому что весь диалог
  остаётся узбекским;
- TC-263 — окна AmoCRM и OnlinePBX, обязательные подсказки и редактор тарифов
  проверяются на RU/UZ без отправки секретов и сохранения; строгий `xfail` по
  BUG-035 фиксирует написание `onlinePBX` вместо `OnlinePBX` в узбекском
  заголовке;
- TC-264 — отдельная закрытая смена с одним перерывом проверяется на экране
  «Рабочее время» Оператора и в «Посещаемости» РОП: RU/UZ переводят
  заголовки, статусы, кнопки, дни недели, KPI и колонки, не меняя строку
  данных; тест не отправляет UI-изменений и удаляет смену с оператором;
- TC-265 — завершение смены во время активного перерыва проверяется на RU/UZ,
  а API-конфликт перерыва без смены остаётся структурированным; строгий
  `xfail` по BUG-036 фиксирует сырой узбекский backend-текст на русском
  экране, временная смена и оператор удаляются;
- TC-266 — browser title страницы входа, тарифов, лидов, рабочего времени,
  посещаемости и звонков сравнивается с языком и видимым заголовком; строгий
  `xfail` по BUG-037 фиксирует узбекские hardcoded-title в RU и технический
  `Sign in | Jwt` на входе;
- TC-267 — на подменённых только в браузере GET-данных сверяются
  подтверждённый формат даты лида, стабильная дата/время смены и цена
  `1234567` с RU/UZ-валютой; момент времени и числовое значение не меняются,
  изменяющие запросы не отправляются;
- TC-268 — вход и 12 основных разделов всех ролей проверяются на RU/UZ:
  видимые заголовки подтверждают загрузку локали, а DOM не содержит сырых
  ключей `nav.*`, `plans.*`, `validation.*`, а также отдельных
  `undefined/null`; пользовательские данные не считаются переводом;
- TC-269 — подменённые только в браузере компания, оператор, лид, сделка и
  статус AmoCRM с кириллицей, латиницей, апострофами и emoji сравниваются
  посимвольно после RU→UZ→RU; штатный heartbeat перехвачен локально, а
  сохранение, PATCH/PUT/DELETE и другие POST не отправляются;
- TC-270 — после предварительной загрузки RU/UZ язык формы входа и кабинета
  РОП переключается в browser Offline; несохранённые логин и пароль
  сохраняются, после восстановления сети RU продолжает работать, а запросы
  изменения данных и ложные сообщения об успешном сохранении отсутствуют;
- TC-271 — на ширине 360 px при увеличении 200% проверяются RU/UZ-страница
  входа, форма создания оператора, тарифы и рабочее время: ключевые тексты и
  действия видимы, не обрезаны и не перекрываются, диалог и язык доступны с
  клавиатуры; первоначальный кандидат по кнопке «Отмена» вручную отклонён;
- TC-272 — активная смена с завершённым перерывом подменяется только в
  браузере и проверяется RU→UZ→RU: статус, действия и таймер не сбрасываются,
  GET weekly не повторяется, POST смены/перерыва и другие изменения не
  отправляются, штатный heartbeat перехвачен локально;
- TC-273 — отдельный временный Оператор открывает смену через UI: статус,
  растущий таймер и история сверяются с одной открытой записью weekly API;
- TC-274 — быстрый двойной клик «Начать смену» отправляет один POST и
  оставляет ровно одну открытую смену без ошибки и немедленного закрытия;
- TC-275 — открытая смена сохраняет исходное время начала и непрерывный
  таймер после reload, перехода между разделами и logout/login с `returnTo`;
- TC-276 — начало перерыва через UI переводит смену в соответствующий статус,
  показывает открытый интервал и приостанавливает рабочий таймер;
- TC-277 — завершение перерыва сохраняет конец, счётчик и суммарную
  длительность после reload; строгий `xfail` по подтверждённому BUG-038:
  история не показывает длительность отдельного завершённого перерыва;
- TC-278 — три перерыва одной временной смены сохраняются отдельными
  хронологическими интервалами, счётчик и общая длительность совпадают с
  weekly API в пределах посекундного округления и переживают reload;
- TC-279 — без открытой смены UI не предлагает перерыв, прямой POST
  возвращает понятный 409, а weekly остаётся пустым после reload;
- TC-280 — попытка закрыть смену во время активного перерыва возвращает 409
  и не меняет данные; после завершения перерыва смена закрывается штатно;
- TC-281 — закрытие смены фиксирует рабочую длительность и итог перерыва;
  UI-таймер и weekly API больше не растут и не меняются после reload;
- TC-282 — закрытая сегодня смена не создаётся повторно и сохраняет итог;
  строгий `xfail` по подтверждённому BUG-039: UI показывает активную кнопку
  «Начать смену», хотя её нажатие предсказуемо возвращает 409;
- TC-283 — после потерянного запроса либо потерянного ответа открытие смены
  синхронизируется через weekly API и заканчивается одной открытой сменой;
- TC-284 — после сетевого сбоя toggle перерыва не повторяется вслепую:
  фактически активный интервал осознанно завершается, недоставленный не
  создаётся;
- TC-285 — почти одновременные toggle-действия из двух вкладок проверяются
  отдельно для смены и перерыва; оба варианта имеют строгий `xfail` по
  подтверждённому BUG-040: второй запрос сразу выполняет обратное действие;
- TC-286 — рабочий таймер останавливается на активном перерыве, продолжает
  расти после него, а итог равен длительности смены минус перерыв в UI/API;
- TC-287 — короткий перерыв в несколько секунд сохраняется одним
  неотрицательным интервалом без огромных значений и переживает reload;
- TC-288 — недельная сводка Оператора охватывает понедельник–воскресенье,
  показывает семь дней, правильную сумму и не смешивает соседние недели;
- TC-289–TC-290 — ROP листает недельную посещаемость ровно по семь дней без
  перехода в будущее; строки операторов и четыре KPI сверяются с weekly API;
- TC-291–TC-297 — роли и два временных tenant проверяются на изоляцию weekly,
  presence и удаления смен, явный `operator_id` superadmin и невалидные
  UUID/даты; TC-292 имеет strict `xfail` по подтверждённому BUG-043: ROP
  получает presence чужого оператора;
- TC-298–TC-301 — heartbeat проверяется на появление online, окно 90 секунд,
  немедленную отправку после focus и независимость рабочего экрана от 503;
- TC-302–TC-305 — по SQL и backend-контракту проверяется автозакрытие в
  23:59:59 Asia/Tashkent, граница текущего дня и новая смена после полуночи;
  TC-303 имеет strict `xfail` по подтверждённому BUG-044: открытая строка
  break history не получает `ended_at` при автозакрытии смены;
- TC-306–TC-307 — пустая неделя не создаёт фантомные KPI/строки, а очень
  длинное Unicode-имя не ломает прокручиваемую таблицу посещаемости;
- TC-308–TC-313 — локальная безопасная сборка landing проверяется на основные
  секции, якоря CTA, активные тарифы API, mobile/200% reflow, клавиатуру и
  `prefers-reduced-motion`;
- TC-314–TC-317 — demo-заявка проходит от локального landing до mocked списка
  superadmin, CRM enum преобразуются корректно, пробелы нормализуются, а
  обязательные поля блокируют пустой POST;
- TC-318 — strict `xfail` по подтверждённому BUG-041: текущий HTML `pattern`
  не компилируется, поэтому demo-форма отправляет телефон с буквами и
  слишком короткое значение;
- TC-319–TC-320 — длинные Unicode-данные сериализуются без падения, а HTML/XSS
  из заявки отображается в admin только текстом;
- TC-321 — strict `xfail` по подтверждённому BUG-042: до перерисовки
  disabled-кнопки быстрый двойной клик отправляет два одинаковых POST;
- TC-322–TC-328 — после сетевой ошибки возможен retry без повторного ввода,
  HTTP 500 не показывает ложный успех, сбой Google Sheets не теряет запись БД,
  новый/legacy routes совместимы, валидация и RBAC API соблюдаются, а список
  лидов сортируется newest-first и запрашивает следующую страницу API;
- TC-364 — карточки двух выбранных операторов сохраняют правильные URL и
  профиль после переключения и перезагрузки;
- TC-365 — первая страница истории двух операторов серверно изолирована по
  `operator_id` и совпадает с API;
- TC-370 — базовые Play/Pause записи звонка в карточке оператора
  (`xfail`, подтверждённый BUG-026).
- BUG-045 — отдельная read-only API-проверка сравнивает первую страницу
  звонков одного оператора при `perPage=6`, `30` и `100`; строгий `xfail`
  фиксирует исчезновение существующих звонков из-за фильтрации после
  пагинации.
- TC-372 — несуществующие оператор, сделка, поле и лид дают безопасный
  404-state; вариант лида помечен `xfail` по подтверждённому BUG-031:
  backend возвращает HTTP 500 Google Sheets вместо 404.
- TC-373 — `healthz`, `readyz` и Prometheus-метрики доступны, соответствуют
  контракту и не раскрывают секреты/персональные данные; повторная проверка
  выполняется после безопасного бизнес-запроса. Проверка после реального
  телефонного звонка остаётся ручной частью кейса.
- TC-375 — чистая операторская сессия загружает актуальные JS/CSS основных
  маршрутов без 404, Console/Page Error и router error, в том числе после
  reload. Вкладка, открытая до нового деплоя, проверяется во время релиза.
- TC-377 — список и форма создания оператора остаются доступны на
  1280×720, 1366×768, 1920×1080 и при CSS-viewport, эквивалентном масштабу
  200%; после возврата размера раскладка восстанавливается.
- TC-378 — вход РОП, навигация, select, дата, focus trap и закрытие формы
  выполняются только клавиатурой; изменяющий POST не отправляется.
- TC-379 — медленное сохранение оператора блокирует повторный клик, отправляет
  один `PATCH` и сверяет результат через API (`xfail`, подтверждённый BUG-030:
  кнопка сереет, но progressbar, текст ожидания и `aria-busy` отсутствуют).
- TC-382 — logout закрывает SSE и не возвращает кэш кабинета через Back/reload
  (`xfail`, подтверждённый BUG-029: поток сделок не устанавливает HTTP/SSE-
  соединение). После исправления initial snapshot тот же тест продолжит
  проверку полного logout-сценария.
- TC-400 — CORS разрешает staging-админку и отклоняет неизвестный origin
  (`xfail`, подтверждённый BUG-028: staging отражает произвольный origin и
  разрешает credentials). Изменяющая проверка demo-формы остаётся ручной,
  чтобы не создавать заявки.

TC-011 запускается отдельно и serial, потому что намеренно исчерпывает общий
для IP лимит попыток входа. Тест создаёт временного оператора, проверяет
восстановление после `Retry-After` и удаляет его. TC-013 и TC-019 остаются
длительными сценариями: для них нужно наблюдать
открытую браузерную сессию до 20 минут.

TC-034–TC-038 запускаются одним pytest-процессом. Фикстура берёт реальные
данные текущего staging-РОП только для чтения, создаёт второго РОП и его
оператора на время проверки, а затем удаляет их. TC-037 дополнительно создаёт
у текущего РОП отдельного временного оператора, его тестовую смену и перерыв;
все эти записи также удаляются через `finally`.

## Безопасность тестовых данных

Парольные и межклиентские тесты создают только отдельные временные записи с
уникальными данными. После проверки операторы, смены и временный РОП удаляются
даже при падении. Реальные лиды, воронки, звонки и настройки компании Б
используются только для чтения. Рабочие пользователи и production не
изменяются.

Служебные входы автоматически разнесены минимум на 13 секунд. Это не позволяет
пакету TC-012–TC-020 исчерпать общий staging rate limit — пять попыток входа
за минуту с одного адреса.

## Подготовка

1. Создать виртуальное окружение и установить `requirements.txt`.
2. Установить Chromium:

   ```bash
   python -m playwright install chromium
   ```

3. Скопировать имена переменных из `.env.example` в локальный `.env`.
4. Заполнить абсолютные адреса web и API с `https://`.
5. Заполнить учётные данные только тех ролей, которые участвуют в выбранном
   пакете. Super-admin не обязателен для ROP/operator-тестов.

Секреты и адреса окружений нельзя записывать в тесты, документацию или Git.

## Запуск

Новый пакет управления сессией и паролями:

```bash
python -m pytest \
  autotests/tests/api/auth \
  autotests/tests/web/auth/test_tc_016_tc_017_password_validation.py \
  autotests/tests/web/auth/test_tc_020_double_submit.py
```

Пакет управления операторами:

```bash
python -m pytest \
  autotests/tests/api/users \
  autotests/tests/web/users
```

Один тест:

```bash
python -m pytest \
  autotests/tests/api/auth/test_tc_012_deactivated_operator.py
```

Проверка списка тестов без обращения к staging:

```bash
python -m pytest --collect-only -q autotests/tests
```

Headless-режим включён по умолчанию. Trace и screenshot сохраняются только при
падении.
## Ежедневный happy-path UAT

Утверждённый набор выбирается отдельным маркером и не копирует регресс:

```bash
.venv/bin/python scripts/run_daily_uat.py --telegram auto
```

Runner собирает 33 pytest-item из `autotests/tests/uat`, создаёт уникальный
`uat-results/<timestamp>`, формирует `report.txt` и `summary.json`, затем при
полной Telegram-конфигурации доставляет человеческий отчёт. Неподготовленный
ресурс отображается как «не выполнено», известный дефект — отдельно как
`blocked_defect`; оба состояния запрещено считать `pass`.

Источник UAT-ID, шагов и ожиданий:
`qa-docs/daily-uat-checklist.json`. Правила настройки и сопровождения:
`qa-docs/14-daily-uat-operations.md`.
