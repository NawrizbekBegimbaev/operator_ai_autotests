1. ПРОВЕРИЛИ НАСТРОЙКУ CORS — TC-400
-------------------------------------

CORS — это правило браузера, которое определяет, каким внешним сайтам
разрешено обращаться к API от имени пользователя.

Проверку выполнили вручную через безопасный запрос OPTIONS и затем закрепили
автотестом.

Результат на staging:

- неизвестный внешний origin был принят сервером;
- сервер вернул этот origin в `Access-Control-Allow-Origin`;
- одновременно было разрешено
  `Access-Control-Allow-Credentials: true`;
- разрешены заголовок Authorization и основные изменяющие HTTP-методы.

Это не означает, что любой сайт автоматически получает пароль или токен.
Однако при наличии браузерной сессии, ошибке в хранении токена либо другой
точке входа такая настройка снимает важный защитный барьер.

После ручного обсуждения отклонение признано реальным дефектом уровня P2.

Создан BUG-028:
«API разрешает credentialed CORS-запросы с любого внешнего origin».

Автотест TC-400:

- подтверждает доступ разрешённого origin staging;
- отправляет preflight от неизвестного origin;
- требует, чтобы неизвестный origin был отклонён;
- помечен строгим ожидаемым падением по BUG-028;
- не отправляет изменяющие запросы и не создаёт данные.


2. ПРОВЕРИЛИ REALTIME-ПОТОК СДЕЛОК — TC-382
--------------------------------------------

Раздел «Звонки» должен получать изменения списка сделок через SSE.

SSE можно сравнить с постоянно открытой линией: сервер не ждёт, пока
пользователь обновит страницу, а сам отправляет новое состояние списка.

На staging установлено:

- запрос к `/v1/amocrm/deals/stream` отправляется;
- HTTP-ответ не начинается;
- заголовок `Content-Type: text/event-stream` не приходит;
- начальный снимок списка не отправляется;
- heartbeat не приходит;
- интерфейс не получает realtime-обновления;
- длительное ожидание в Safari не изменило результат.

Проверка повторялась отдельно, чтобы исключить случайную задержку браузера.

Создан BUG-029:
«SSE-поток сделок зависает без HTTP-ответа и realtime-обновлений».

Автотест TC-382 сохраняет сильную проверку полного сценария выхода:

- открывает поток в авторизованной сессии;
- после исправления будет требовать начальный snapshot;
- выполняет logout;
- проверяет закрытие потока;
- проверяет, что Back и reload не возвращают закрытые данные кабинета.

Пока начальное соединение отсутствует, тест строго ожидаемо падает по BUG-029.


3. ПРОВЕРИЛИ МЕДЛЕННОЕ СОХРАНЕНИЕ — TC-379
-------------------------------------------

Для формы редактирования оператора искусственно задержали ответ PATCH, чтобы
увидеть состояние интерфейса во время ожидания.

Фактическое поведение:

- после нажатия «Сохранить» кнопка становится серой и недоступной;
- повторный запрос не отправляется;
- текст кнопки не меняется;
- spinner или progressbar отсутствует;
- `aria-busy` отсутствует;
- пользователь видит только серую кнопку и не понимает, выполняется ли
  сохранение или интерфейс завис.

После ручной проверки отсутствие понятной обратной связи признано дефектом
удобства использования и доступности.

Создан BUG-030:
«При медленном сохранении оператора нет понятного индикатора загрузки».

Автотест TC-379:

- задерживает только тестовый PATCH;
- подтверждает блокировку повторного нажатия;
- требует видимый или доступный индикатор ожидания;
- проверяет ровно один PATCH;
- после ответа сверяет сохранённое значение через API;
- возвращает исходное значение при завершении;
- строго ожидаемо падает по BUG-030.


4. УТОЧНИЛИ TC-053 ПО РЕЗУЛЬТАТАМ РУЧНОЙ ПРИЁМКИ
-------------------------------------------------

TC-053 проверяет пустую форму создания оператора.

Ручная проверка подтвердила:

- для имени, фамилии, пароля, имени пользователя и зарплаты после выхода из
  пустого поля показываются подсказки;
- для телефона, PBX extension и дня зарплаты отдельная подсказка после
  простого входа в поле и выхода из него может не появляться;
- при этом кнопка «Создать» остаётся неактивной;
- `POST /v1/operators` не отправляется.

По решению тестировщика отсутствие трёх отдельных подсказок является
допустимым текущим поведением, а не дефектом.

Контракт TC-053 уточнён по факту 30.07.2026:

- ложный баг не создавался;
- xfail не добавлялся;
- главная защита от отправки пустой формы сохранена;
- автоматическая проверка прошла на staging.


5. УТОЧНИЛИ ГРАНИЦУ ЗАРПЛАТЫ — TC-056
--------------------------------------

TC-056 проверяет отрицательное, нулевое и положительное значение зарплаты.

Ручная и автоматическая диагностика показала:

- при попытке ввести `-1` поле не принимает знак минус;
- в поле остаётся положительное значение `1`;
- отрицательное число в форму фактически не попадает;
- значение `0` вызывает сообщение «Укажите зарплату»;
- при нуле кнопка «Создать» неактивна;
- положительное значение `1000000` принимается без ошибки.

Ранее тестировщик уже подтвердил фильтрацию минуса как корректное поведение.

Контракт TC-056 уточнён по факту 30.07.2026:

- попытка отрицательного ввода проверяется как фильтрация знака;
- ноль по-прежнему должен отклоняться;
- положительное число должно приниматься;
- тест не нажимает «Создать» и не отправляет POST;
- автоматическая проверка прошла на staging.


6. ПРОВЕРИЛИ ПОЛНУЮ СМЕНУ РОЛИ — TC-043
----------------------------------------

Автотест повторяет реальный сценарий в одном браузере:

1. Вход под РОП.
2. Открытие административного раздела.
3. Выход.
4. Вход под Оператором без закрытия браузера.
5. Проверка нового API-профиля, локального хранилища и меню.
6. Попытка открыть прямую ссылку на раздел РОП.

Подтверждено:

- API возвращает роль Оператора;
- старое состояние РОП заменяется;
- меню содержит только операторские разделы;
- защищённые данные РОП не появляются;
- запрос защищённого раздела не выполняется.

TC-043 прошёл.


7. ПОДГОТОВИЛИ СОЗДАНИЕ РОП — TC-044
-------------------------------------

Создан автоматический сценарий, который должен:

- войти под Super-admin;
- заполнить форму нового РОП уникальными данными;
- выбрать тариф;
- проверить успешный POST;
- найти ровно одну новую строку;

Поэтому TC-044:

- не создавал пользователя;
- завершился явным `skip` с понятной причиной;
- готов к запуску после добавления отдельной тестовой учётной записи.
